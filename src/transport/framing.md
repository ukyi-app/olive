# 바이트 틀 (`framing.ts`)

연결(상호 TLS) 위의 바이트를 틀로 자르고 잇는다. 계약 v1 밖의 전송 형식이다. 봉투의 서명과 동작은 보지 않고(받는 쪽 `verifyEnvelope`의 일), 자격 값을 쓸지도 정하지 않는다(받는 쪽이 서명된 시작 지시의 지문과 대조한다). 이 모듈은 형식만 본다.

## 머리

모든 틀은 머리 4바이트로 시작한다. 첫 바이트가 종류이고, 뒤 3바이트가 길이(부호 없는 정수, big-endian)다. 종류는 첫 바이트만으로, JSON 해석 전에 정한다.

| 첫 바이트 | 종류 | 길이가 세는 것 | 받는 길이 |
|---|---|---|---|
| `0x00` | 봉투 | 봉투 바이트 | 1 ~ 65,536 (`MAX_MESSAGE_BYTES`) |
| `0x01` | 자격 값 | 값 바이트(실행 ID·지문 100바이트는 빼고) | 1 ~ 16,384 (`CREDENTIAL_MAX_BYTES`) |
| 그 밖 | 없음 | | 그 한 바이트에서 `frame_unknown_kind` |

## 봉투 틀

| 위치(바이트) | 크기 | 내용 |
|---|---|---|
| 0 | 1 | `0x00` |
| 1 ~ 3 | 3 | 봉투 길이 N |
| 4 ~ 3+N | N | 봉투(UTF-8 JSON) |

봉투 상한이 64KiB(`0x010000`)라 4바이트 길이 접두의 첫 바이트는 늘 0이다. 그 0을 봉투 종류로 읽으므로 봉투 틀은 "4바이트 big-endian 길이 + 봉투"와 바이트가 같다. 본문이 다 오면 UTF-8, 문법, 중복 키, 깊이를 해석 전에 본다(`framing.ts` 머리 주석).

## 자격 값 틀

| 위치(바이트) | 크기 | 내용 |
|---|---|---|
| 0 | 1 | `0x01` |
| 1 ~ 3 | 3 | 값 길이 L |
| 4 ~ 39 | 36 | 실행 ID. ASCII, 계약 v1의 UUID 꼴(소문자 16진 `8-4-4-4-12`) |
| 40 ~ 103 | 64 | 지문. ASCII, 값의 SHA-256을 소문자 16진 64자로 |
| 104 ~ 103+L | L | 값 바이트. 해석하지 않는다 |

틀 하나는 104 + L바이트이고 최대 16,488바이트다. 머리와 값은 JSON이 아니다.

받는 순서: 머리 4바이트에서 종류와 길이(0, 상한 초과)를 본다 → 실행 ID·지문 100바이트를 다 받으면 꼴을 본다 → 그 뒤에야 값 버퍼(L바이트)를 잡는다. 어느 단계에서 거절해도 거절된 틀 자체의 바이트는 반환값·사유·오류로 나가지 않는다. 같은 push에서 그 앞에 완성된 정상 틀은 거절과 함께 돌아온다(아래 "거절").

**값 틀에는 서명·시한·nonce가 없다.** 누가 보냈는지는 연결의 상호 TLS 신원이, 어느 값을 쓸지는 서명된 시작 지시(`task_start`·`session_start`의 `credential.digest`)와의 지문 대조가 정한다. 둘 다 이 모듈 밖이다.

## 디코더 둘

| 함수 | 받는 틀 | 값 틀을 받으면 |
|---|---|---|
| `createFrameDecoder` | 봉투만 | 머리 4바이트를 한 정수(16,777,216 이상)로 읽어 `frame_too_large`. 버퍼를 잡지 않고 디코더가 끝난다 |
| `createMixedFrameDecoder` | 봉투와 값 | `{ kind: "credential", credential: { runId, digest, value } }`로 낸다 |

섞어 받는 디코더는 틀을 받은 순서대로 `frames`에 낸다. 봉투 틀은 봉투만 받는 디코더와 같은 검사, 같은 결과, 같은 `heldBytes()`다(`test/transport/credential-frame.test.ts`가 대조한다). 거절하면 디코더는 끝나고 다시 동기화하지 않는다.

값 틀의 거절 사유. 봉투만 받는 디코더는 다섯 가운데 어느 것도 내지 않는다. `frame_unknown_kind`만 섞어 받는 디코더 전용이고, 나머지 넷은 만드는 함수(`encodeCredentialFrame`)도 낸다. 계약 v1의 사유와 겹치지 않는다.

| 사유 | 때 | 내는 곳 |
|---|---|---|
| `frame_unknown_kind` | 첫 바이트가 `0x00`·`0x01`이 아니다 | 섞어 받는 디코더 |
| `frame_credential_empty` | 값 길이 0 | 섞어 받는 디코더, 만드는 함수 |
| `frame_credential_too_large` | 값 길이가 `CREDENTIAL_MAX_BYTES`를 넘는다 | 섞어 받는 디코더, 만드는 함수 |
| `frame_credential_bad_run_id` | 실행 ID 칸이 UUID 꼴이 아니다 | 섞어 받는 디코더, 만드는 함수 |
| `frame_credential_bad_digest` | 지문 칸이 소문자 16진 64자가 아니다 | 섞어 받는 디코더, 만드는 함수 |

값 틀의 중간에서 온 끝 알림은 `frame_truncated`, 끝 알림 뒤의 조각은 `frame_after_end`다(봉투 틀과 같은 사유).

### 거절

거절된 틀 자체의 바이트는 반환값·거절 사유·오류에 실리지 않는다. 거절 사유는 `rejected`에 이름으로 돌려준다. 거절과 함께 돌아온 step에는 그 앞에 완성된 정상 값 틀이 들어 있을 수 있다. 진단에는 `rejected`의 이름만 쓰고 step·완성된 값 틀·만든 틀을 통째로 기록하지 않는다. 앞선 정상 값의 소유는 받은 쪽에 있다(쓰거나 버릴 때 0으로 채운다).

조립 중인 값과 실행 ID·지문 칸은 디코더의 `#` 비공개 필드에 있어 디코더 객체의 `JSON.stringify`·`Object.keys`·`String()`에 나오지 않는다(시험). 완성된 값 틀(`DecodedCredential`)이 든 `push`의 결과나 `encodeCredentialFrame`의 성공 결과는 값을 담은 보통 객체라 직렬화하면 값이 나온다.

## 고른 것과 까닭

- **종류를 머리의 첫 바이트에 둔다.** 봉투 틀이 한 바이트도 바뀌지 않아 `encodeFrame`·`createFrameDecoder`를 부르는 곳을 고치지 않는다. 값을 받지 않는 쪽은 봉투만 받는 디코더를 그대로 쓰고, 그 디코더는 값 틀을 봉투로 해석하지 않고 닫는다.
- **길이 칸은 값만 센다.** 0과 상한 초과가 머리 4바이트에서 바로 보인다(봉투 틀의 `frame_empty`·`frame_too_large`와 같은 자리).
- **실행 ID와 지문을 ASCII 글로 둔다.** 시작 지시에 서명된 `run_id`·`credential.digest`와 같은 꼴이라 받는 쪽이 변환 없이 같은 글로 대조한다(`credentialMatches`는 소문자 16진 글을 받는다). 꼴이 틀린 머리(대문자, 16진이 아닌 글자, `-`의 자리)를 거절할 수 있다. 이진(16 + 32 = 48바이트)이면 ASCII 100바이트에서 52바이트를 아끼지만 어떤 바이트열도 올바른 값이라 꼴 검사가 없다.
- **값은 해석하지 않는다.** JSON 해석기와 `TextDecoder`를 지나지 않고, 받은 바이트를 그 값만 담는 새 배열로 낸다. 받는 쪽은 그 바이트로 지문을 대조한다.

## 값의 상한 `CREDENTIAL_MAX_BYTES` = 16,384

- 실제 토큰의 크기는 확인하지 않았다.
- 실행기는 값을 환경 변수 하나로 모델 CLI에 넘기고(`src/executor/profile.ts`의 `launchPlan`), CLI가 그 값을 HTTP 머리에 실어 쓴다고 보았다(추론). Node.js와 Bun이 받는 HTTP 머리 전체의 기본 상한(`http.maxHeaderSize`)이 16,384바이트다. 그보다 큰 토큰은 흔한 HTTP 구현에 기본 설정으로 닿지 못하므로 이 값을 넉넉한 상한으로 삼았다.
- 65,436(= 65,540 − 4 − 100)까지는 올려도 미완성 틀의 메모리 상한이 그대로다. 그보다 크면 그 상한도 커진다.
- 보내는 쪽이 값을 읽을 때의 상한은 이 값 이하로 둔다. 넘는 값은 틀로 만들 수 없다(`encodeCredentialFrame`이 `frame_credential_too_large`).

## 메모리

- push 호출 사이에 디코더가 쥐는 미완성 틀: 봉투 틀 4 + 65,536 = 65,540바이트, 값 틀 4 + 100 + 16,384 = 16,488바이트. 두 디코더 모두 `heldBytes()`는 65,540 이하다.
- 한 번의 push가 돌려주는 바이트(봉투 바이트, 값 틀의 실행 ID·지문 100과 값)는 이 상한에 들지 않고 넣은 조각 + 직전에 쥐던 미완성 틀 이하다. 부르는 쪽이 조각의 크기로 묶는다.
- 거절하거나 끝 알림이 틀의 중간에 오면 쥐던 버퍼를 놓는다. 덜 온 값 버퍼는 놓기 전에 0으로 채운다.

## 이 모듈 밖에서 지킬 것

- 값 틀은 맞춘(정지 세대를 맞춘) 연결에서만 받는다. 값 틀을 봉투 검증(`verifyEnvelope`, `link.receive`)으로 넘기지 않는다.
- 받은 값은 쓰거나 버린 뒤 0으로 채운다. 거절과 함께 온 step의 앞선 정상 값, 쓰지 않는 값도 같다. 그 값의 소유는 받은 쪽에 있다.
- 보내는 쪽은 `encodeCredentialFrame`에 넘긴 값과 돌려받은 틀을 소켓이 그 버퍼를 놓은 뒤(쓰기가 끝난 뒤) 0으로 채운다. 쓰기 전에 채우면 0이 나간다.
- 값과 틀의 원문을 로그, 장부, 재전송, outbox, 진단에 두지 않는다. 거절을 기록할 때도 `rejected`의 이름만 쓴다. step, `DecodedCredential`, `encodeCredentialFrame`의 성공 결과를 통째로 직렬화하거나 출력하면 값이 따라간다.
