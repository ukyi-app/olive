# olive-control/v1 요약

감독, 실행기, 현관이 함께 쓰는 계약이다. 코드는 `src/contract/v1/`(공개 면은 `index.ts`), 사례는 `contracts/fixtures/v1/`. 설계의 기준은 homelab `docs/plans/2026-11-13-olive/supervisor.md` §9다. 표와 코드가 다르면 코드가 맞고, 이 표를 고친다.

## 봉투

연결 위의 메시지는 모두 `{ header, signature, body }`다. 세 칸 밖의 칸, 머리·본문의 모르는 칸은 거절한다.

| 머리 칸 | 값 |
|---|---|
| `contract` | `"olive-control/v1"` |
| `sender`, `recipient` | `supervisor`, `front-door`, `executor/<session\|역할>/<인스턴스>/<저장소>` |
| `action` | 아래 21개 |
| `request_id` | 소문자 UUID |
| `stop_generation` | 정지 세대(0 이상 정수). 받는 쪽의 값과 정확히 같아야 한다. 예외는 아래 "정지 세대 올리기"의 **정확 일치 규칙**에만 적는다 |
| `run_generation` | 본문이 가리키는 실행의 세대. 실행에 묶이지 않는 메시지는 0 |
| `body_digest` | 본문 정규 직렬화의 SHA-256, 소문자 16진 |
| `issued_at`, `expires_at` | Unix epoch 밀리초. 수명은 0 초과 30초 이하(`MESSAGE_TTL_MAX_MS`). 정지 세대 맞춤의 두 메시지는 15초 이하(`STOP_SYNC_TTL_MAX_MS`). 두 상한은 받는 쪽 경계라 v1에 고정 |
| `nonce` | 소문자 16진 32자. 낸 쪽마다 한 번 |

**서명 대상:** `header` 전체의 정규 직렬화를 UTF-8로 쓴 바이트. Ed25519, base64url(패딩 없음, 86자). 다시 써서 같은 표기만 받는다.

**정규 직렬화:** RFC 8785(JCS)의 부분집합. 키는 UTF-16 코드 단위 순서, 공백 없음, 문자열은 JCS 이스케이프. 숫자는 안전 정수만(소수·지수 없음, `-0`은 `0`). 짝 없는 서로게이트(값과 객체의 키 모두), 깊이 16 초과는 받지 않는다. 받는 쪽은 받은 바이트가 아니라 해석한 값으로 다시 만들어 서명을 확인한다.

**검증 순서:** 모양(봉투 → 계약 판 → 동작 → 머리) → 서명 → 방향 → 받는 쪽 → 시한 → 본문(digest → 금지 칸 → 모양 → 관계 → 받는 시각 기준의 관계) → (맞춤 답이면 challenge) → 정지 세대 → 상태 목록의 실행 세대 → 실행 세대 → nonce. 이유는 `envelope.ts`의 `verifyEnvelope` 주석에 있다. nonce는 받아들일 봉투만 쓴다.

**결과:** 통과하면 `{ ok: true, action, header, body, sender, recipient, adoptedStopGeneration }`, 거절이면 `{ ok: false, reason }`(사유 하나). `adoptedStopGeneration`은 이 봉투로 받는 쪽의 정지 세대가 올라갔으면(받는 쪽에 세대가 없어 맞춤 답으로 처음 정했으면) 그 값, 아니면 `null`이다. fixture의 `expect`도 같은 값을 `adopted_stop_generation`으로 적는다.

## 정지 세대 올리기

비상 정지(supervisor.md §7.3)는 감독이 새 정지 세대를 적용하고, 권한을 끊고, 실행기에 종료를 지시하는 순서다.

- **더 높은 정지 세대를 받아들이는 길은 둘뿐이다.**
  1. **아는 실행의 비상 종료:** `reason: "emergency_stop"`인 `task_cancel`과 `session_stop`. 받는 쪽이 아는 실행을 닫으며 새 세대를 옮긴다(`unknown_run`은 그대로라 쥔 실행이 없으면 이 길은 없다).
  2. **연결할 때의 맞춤:** `stop_sync_reply`(아래 "연결할 때 정지 세대 맞추기"). 쥔 실행이 없는 실행기, 감독이 없어 종료를 못 받은 실행기, 저장소를 잃은 실행기가 이 길로 지금의 세대를 받는다.
- **정확 일치 규칙.** 받는 쪽은 머리 `stop_generation`이 자기 세대와 정확히 같은 봉투만 받는다. 예외는 셋뿐이다. 위의 두 길(더 높은 세대를 받아들임), 그리고 감독이 받는 `stop_sync_request`(머리는 늘 0이고 감독의 세대와 대조하지도 올리지도 않는다. 감독의 세대가 `null`이면 거절). 그래서 연결의 첫 메시지는 맞춤 요청이고, 감독이 정확 일치로 보는 첫 메시지는 맞춤 뒤의 첫 일반 메시지인 `hello`다. 이 밖의 모든 동작(시작·갱신·확정, 다른 사유의 종료·취소, 영수증·보고, `hello`·`status_query`·`status_report`·`ack`)이 더 높은 세대를 실어 오면 `stop_generation_mismatch`다.
- **세대는 내려가지 않는다.** 받는 쪽보다 낮은 값은 비상 종료든 맞춤 답이든 거절한다. 새 세대를 받아들인 뒤에는 옛 세대의 시작·갱신이 서명과 시한이 맞아도 `stop_generation_mismatch`다.
- **왜 종료 지시도 길인가:** 설계의 순서가 "감독이 종료를 지시한다"이고, 종료는 실행을 닫기만 하므로 미래 세대를 받아도 새로 열리는 것이 없다.

## 연결할 때 정지 세대 맞추기

관리자 결정(2026-11-18): 실행기는 감독에 붙는 첫 단계에서 감독이 서명한 지금의 정지 세대를 받아, 올라가는 방향으로만 맞춘다. 연결(D-55: 실행기가 먼저 붙어 유지)과 인증(D-58: mTLS + Ed25519)을 그대로 쓰고 새 구성 요소를 두지 않는다.

```text
실행기                                         감독(최신 정지 기록 복원 뒤)
  │ 인증된 연결을 연다(mTLS)                       │
  │ challenge = 새 무작위 128비트                  │
  │── stop_sync_request {challenge} ───────────▶│  머리 stop_generation 0. 감독의 세대를 바꾸지 않는다
  │ (실은 때부터 25초 미만만 그 challenge를 기다림)   │  받은 뒤 5초(STOP_SYNC_ANSWER_MAX_MS) 미만에 답을 싣는다
  │◀── stop_sync_reply {challenge} ─────────────│  머리 stop_generation = 감독의 지금 세대, 수명 15초 이하
  │ 검증 → adoptedStopGeneration                 │
  │ (지속 저장 + 낮은 세대의 새 실행 막기, 한 번에) │
  │── hello (맞춘 세대로 정확 일치) ─────────────▶│  맞춤 뒤의 첫 일반 메시지. 여기서부터 평소의 연결(connected)
```

**받아들이는 조건**(`stop_sync_reply`, 실행기에서. 앞의 봉투 검증을 모두 통과한 뒤):

1. 낸 쪽이 `supervisor`이고 감독의 키로 서명했다. 실행기·현관 이름이면 `wrong_direction`, 감독 이름에 다른 키면 `bad_signature`.
2. 받는 쪽 이름이 이 실행기(역할·인스턴스·저장소 ID까지)와 같다. 아니면 `wrong_recipient`.
3. 수명이 0 초과 15초(`STOP_SYNC_TTL_MAX_MS`) 이하이고 지나지 않았다. 아니면 `lifetime_invalid`·`expired`. 답의 신선도는 답의 발급 시각부터 잰다.
4. 본문은 `challenge` 하나뿐이다. 실행 ID·자격 같은 칸은 `unknown_field`, 명령·이미지 등은 `forbidden_field`. 머리 `run_generation`은 0.
5. 본문의 `challenge`가 이 연결에서 보내고 기다리는 값(`VerifyContext.stopSyncChallenge.challenge`)과 같고, 그 요청을 실은 시각(`sentAt`, 실행기 시계의 안전 정수 밀리초)부터 잰 경과 시간 `now - sentAt`이 0 이상 25초(`STOP_SYNC_WAIT_MS`) 미만이다. 기다리는 값이 없거나, `challenge`가 다르거나, `sentAt`이 없거나 안전 정수가 아니거나, `sentAt`이 `now`보다 미래이거나, 기한 정각 이후면 `challenge_mismatch`. 기한은 3의 신선도와 따로 잰다.
6. 머리 `stop_generation`이 실행기의 세대보다 낮지 않다. 낮으면 `stop_generation_mismatch`. 같으면 `adoptedStopGeneration: null`, 높으면 그 값. 실행기에 세대가 없으면(`null`) 어떤 값이든(0 포함) 그 값.
7. nonce가 처음이다. 아니면 `replayed`.

**기다리는 기한의 식.** 이 계약의 시한은 모두 정각부터 거절한다(봉투는 `expires_at` 정각에 `expired`, 맞춤 대기는 기한 정각에 `challenge_mismatch`). 그래서 전달 상한과 처리 상한은 "그 값 미만"이다: 요청의 전달 `d₁ < DELIVERY_MAX_MS`, 감독의 처리 `a < STOP_SYNC_ANSWER_MAX_MS`, 답의 전달 `d₂ < DELIVERY_MAX_MS`. 그러면 `d₁ + a + d₂ < 2 × DELIVERY_MAX_MS + STOP_SYNC_ANSWER_MAX_MS ≤ STOP_SYNC_WAIT_MS`이므로 상한을 지킨 왕복은 기한 안에 든다. 지금 값은 25초 = 2 × 10초 + 5초(등호)라, 세 상한에 정각으로 걸린 왕복(10초 + 5초 + 10초)은 상한을 넘은 것이고 거절된다(시험이 고정한다). 기한은 실행기가 거절하는 경계라 v1에 고정이고, 전달 상한과 처리 상한(기본값)은 이 식을 지키는 안에서만 바꾼다(시험이 지킨다). 기한을 늘려도 받는 답은 이 연결에서 기다리는 challenge를 담은 답뿐이다.

**요청**(`stop_sync_request`, 감독에서): 본문은 `challenge` 하나뿐이고 머리 `stop_generation`은 0, `run_generation`은 0이어야 한다(아니면 `stop_generation_mismatch`·`run_generation_mismatch`, 본문에 세대를 실으면 `unknown_field`). `sealEnvelope`도 이 두 0(답은 `run_generation` 0)이 아니면 서명하기 전에 같은 사유로 거절한다. 감독의 세대와 대조하지도 올리지도 않는다(`adoptedStopGeneration`은 늘 null). 감독의 세대가 없으면(`null`, 정지 기록 복원 전) 요청부터 `stop_generation_mismatch`라 답을 만들 길이 없다.

**세대 없음(`null`)과 0을 가른다.** 0은 "한 번도 정지하지 않았다"는 알려진 세대다. 저장소를 잃었거나 처음 뜬 실행기는 세대를 모르므로 `VerifyContext.stopGeneration`을 `null`로 둔다. `null`이면 맞춤 답 밖의 모든 메시지가 `stop_generation_mismatch`다. 0으로 시작하게 하면 맞춤 없이 우연히 통과하거나, 지금 세대가 0인지 모르는 채 0의 메시지를 받는다.

**이것은 지시가 아니고 허가가 아니다.** 두 메시지는 전송(`transport`)이고 지시 여섯에 들지 않는다. 실행을 지목하지 않고(`runField` 없음, `run_generation` 0) 실행·자격·명령을 싣지 않는다. 세대를 맞춘 것은 정지 해제나 실행 허가가 아니다. 정지 중이면 감독은 접수를 닫아 두므로 맞춘 뒤에도 시작 지시(`task_start`·`session_start`)는 오지 않는다. 시작은 늘 따로 서명된 시작 지시로만 열린다.

## 리뷰가 적은 위험과 다룬 방법

| 위험 | 계약이 막는 것 | 구현의 책임 |
|---|---|---|
| 옛 답의 재생 | 답은 이 연결의 `challenge`에 묶이고(`challenge_mismatch`), 수명 15초, 요청을 실은 뒤 25초 안, nonce 한 번(`replayed`) | 실행기는 연결마다 새 무작위 challenge를 만들고, 답을 받아들이거나, 기다리는 기한이 지나거나, 연결이 끝나면 버린다 |
| 새 저장소에서 과거 값 수용 | 새 저장소 ID로 받는 쪽 이름이 바뀌어 옛 저장소 앞의 답은 `wrong_recipient`. 과거에 서명된 답은 이 연결의 challenge를 담을 수 없다 | 저장소 ID를 다시 쓰지 않는다. 세대가 없는 실행기는 `null`로 둔다(0으로 두지 않는다) |
| 복원 중인 감독이 과거 세대를 서명 | 감독의 세대가 `null`이면 요청을 거절한다 | 감독은 §8의 1단계(최신 정지 기록 적용) 전에는 `stopGeneration`을 `null`로 두고, 장부의 옛 값이나 백업 복원 값을 "지금"으로 쓰지 않는다 |
| 지나치게 큰 값 | 상한을 두지 않는다. 감독의 키로 서명된 답만 받으므로 실행기·현관의 키로는 만들 수 없다 | 감독은 권위 있는 정지 기록의 값만 서명한다. 잘못 들어간 경우의 복구는 실행기 저장소 초기화(새 저장소 ID, `null`에서 다시 맞춤)다 |

상한을 두지 않는 이유: 여러 번의 정지를 놓친 실행기도 한 번에 맞춰야 하므로 "+1만" 같은 증가 폭 제한은 정상 복구를 막는다. 큰 값을 넣을 수 있는 쪽은 감독의 키를 가진 쪽뿐이고, 그 키가 새면 이미 모든 지시를 낼 수 있다.

## 받을 때만 보는 관계

본문 해석기는 `receivedAt`(받는 쪽의 지금 시각)을 받는다. 봉투를 만들 때(`sealEnvelope`)는 `null`이라 발급 시각 기준의 관계만 본다.

- `task_start.deadline_at`: 만들 때는 `issued_at`보다 커야 한다(아니면 `body_malformed`). 받을 때는 받는 시각보다 커야 한다. 같거나 이르면 `deadline_passed`다. 봉투의 30초 시한과 작업 기한은 따로다.

## 지시(감독 → 실행기), 이 여섯뿐

| 동작 | 받는 쪽 | 본문 |
|---|---|---|
| `session_start` | 세션 | `run_id`, `generation_marker_digest`, `takeover_receipt_id`(첫 세션이면 null), `rule_check_id`, `profile_revision`, `policy_revision`, `handoff_digest`, `credential` |
| `session_stop` | 세션 | `run_id`, `reason`(daily_rotation, session_broken, emergency_stop, account_switch) |
| `task_start` | 작업자 | `run_id`, `role`(실행기의 역할과 같아야 함), revision 둘, `snapshot_digest`, `input_digest`, `deadline_at`, `budget_tokens`, `credential` |
| `task_cancel` | 작업자 | `run_id`, `reason`(requested, deadline, budget, emergency_stop) |
| `run_renew` | 둘 다 | `run_id`, `lease_until`(발급 뒤 30초 안) |
| `result_finalize` | 작업자 | `run_id`, `outcome`, `result_digest`(succeeded일 때만), `stored_at` |

`credential`은 자격의 값이 아니라 `account`, `method`, `revision`, `digest`(값의 SHA-256)다. 명령·이미지·볼륨·argv·환경(과 그 변형 이름)의 칸은 어느 깊이에 있든 `forbidden_field`다.

| `status_query` | 감독 → 실행기 | `run_ids`(이미 있는 실행 ID만, 1~8개) |
| `status_report` | 실행기 → 감독 | `in_reply_to`, 실행 상태 |
| `ack` | 감독 → 실행기 | 반영한 영수증·보고 id |
| `stop_sync_request` | 실행기 → 감독 | `challenge`(소문자 16진 32자). 머리 정지 세대 0 |
| `stop_sync_reply` | 감독 → 실행기 | 받은 `challenge`. 머리 정지 세대 = 감독의 지금 세대 |

**실행 상태 항목**(`hello`·`status_report`의 `runs[]`): `run_id`, `state`, `run_generation`, `last_receipt_id`. 같은 `run_id`는 한 메시지에 한 번만 온다.

- `run_generation`은 실행기 장부에 적힌 그 실행의 세대다(서명된 본문 안). `not_known`(실행기에 기록이 없음)이면 `run_generation`과 `last_receipt_id`는 `null`이고, 그 밖의 상태면 `run_generation`은 1 이상이다.
- **감독이 아는 실행**이면 감독 장부의 세대와 같아야 한다. 다르면 봉투째 `run_generation_mismatch`다(옛 세대의 늦게 온 상태).
- **감독이 모르는 실행**(장부 밖)이면 통과한다. 그 세대는 재개나 결과 반영의 권한이 아니다. 그 실행을 닫는 지시(`task_cancel`·`session_stop`의 `run_generation`)와 `status_query`의 대조에만 쓴다. `runsOutsideLedger`가 그런 항목을 고른다(supervisor.md §8의 2).
- **`ready_result`와 `failed_stopped`의 뜻(D-150, 실행기가 지킬 것).** 실행기가 `failed_stopped`로 답한 실행에는 그 종료의 결과 보고(`report_result`)가 없고, 그 뒤에도 결과 보고를 만들지 않으며 `ready_result`로 답하지 않는다. 다시 뜬 뒤의 대조도 같다. `ready_result`는 결과 보고가 있고 아직 확정·정리 전인 실행의 답이다(확정 뒤에는 보고가 남아 있어도 `cleanup_pending`·`finalized`로 답할 수 있다). 종료 확인 영수증(`receipt_stopped`) 뒤 결과 보고가 없는 실행이 모두 `failed_stopped`인 것은 아니다: 띄우기 전에 끝난 실행은 `not_started`로 답한다. 감독은 이 뜻에 기대어 그 실행을 물은 조회의 대조된 답에서 `failed_stopped`이고 `last_receipt_id`가 감독 장부의 종료 영수증 ID와 같은 항목만으로 "결과 없음"을 판정한다(`src/supervisor/dispatch/result-check.md` "결과 없음 판정"). 이 뜻을 어긴 실행기의 늦은 결과 보고는 감독 장부가 받지 않는다(결과가 버려진다). 이 보장은 끊기지 않은 한 실행기 저장소에 대해서다: 옛 사본·스냅샷에서 되살린 저장소의 답은 지키지 못하고 지원 밖이다(운영 규칙 D-170, `README.md` "작업자 실행기가 감독 쪽에 기대는 것"). 칸·값·동작·거절 경계는 그대로라 판을 올리지 않는다.
- **`last_receipt_id`**는 그 실행의 마지막 영수증 ID다(결과 보고 ID는 들지 않는다). 종료 확인 영수증 뒤에 같은 실행의 다른 영수증(종료 뒤에 닿은 취소의 접수 영수증 등)이 생기면 그 ID가 된다.

연결이 살아 있지 않으면 지시를 만들지 않는다(`no_connection`). 남은 시한이 전달 지연 상한(10초, 기본값)보다 짧은 봉투는 싣지 않는다(`too_late_to_send`). 끊김 판정 뒤 끝났다고 증명되지 않은 실행은 `unknown_running`이다. 다시 붙으면 같은 실행 ID를 묻기만 하고 새 실행 ID로 다시 보내지 않는다.

## 거절 사유

`malformed`, `unknown_field`, `contract_mismatch`, `unknown_action`, `unknown_sender`, `bad_signature`, `wrong_direction`, `wrong_recipient`, `lifetime_invalid`, `not_yet_valid`, `expired`, `body_malformed`, `digest_mismatch`, `forbidden_field`, `role_mismatch`, `result_too_large`, `deadline_passed`, `challenge_mismatch`, `stop_generation_mismatch`, `unknown_run`, `run_generation_mismatch`, `replayed`. 전송 규칙: `no_connection`, `too_late_to_send`, `receipt_conflict`.

## 구현이 지킬 것

이 모듈은 받아도 되는 메시지인지만 가른다. 아래는 감독·실행기 구현이 지켜야 계약의 보호가 성립하는 것이다.

- **새 정지 세대의 적용은 실행기의 일이다.** `adoptedStopGeneration`이 null이 아니면(비상 종료든 맞춤 답이든), 그 봉투의 효과를 내기 전에 새 세대를 지속 상태 저장소에 적고 그보다 낮은 세대의 지시로 새 실행이 열리지 않게 막는 일을 한 번에(원자적으로) 한다. 저장할 때도 단조 증가를 다시 확인한다(동시에 온 더 높은 세대를 낮은 값으로 덮지 않는다). 적지 못했으면 종료는 하되 새 지시를 받지 않고, 맞춤이면 연결을 끊고 다시 맞춘다.
- **감독은 최신 정지 기록을 복원한 뒤에만 맞춤에 답한다.** supervisor.md §8의 1단계(더 새로운 정지 세대를 먼저 적용) 전에는 `stopGeneration`을 `null`로 두어 요청을 거절한다. 답의 세대는 감독 자신의 정지 기록에서만 온다. 요청을 보낸 실행기의 어떤 값(머리, 본문, `hello`)도 감독의 세대를 바꾸지 않는다.
- **맞춤은 연결마다 한 번, `hello`보다 먼저다.** 실행기는 연결마다 새 무작위 challenge(128비트 이상)를 만들어 한 번만 쓴다. 같은 연결에서 세대가 어긋나면 연결을 끊고 새 연결에서 다시 맞춘다.
- **기다리는 challenge를 버리는 때는 셋이다.** 실행기는 요청을 연결에 실은 실제 시각을 `now`와 같은 시계의 `sentAt`으로 함께 두고(다른 요청의 시각을 다시 쓰지 않는다), (1) 그때부터 `STOP_SYNC_WAIT_MS`(25초)가 되거나 (2) 그 연결이 끝나거나 (3) 맞춤이 성공하면 challenge를 버린다(`stopSyncChallenge`를 `null`로). 버린 뒤 온 답은 `challenge_mismatch`다. 기한이 지났으면 그 연결을 끊고 새 연결에서 새 challenge로 다시 맞춘다. 기한은 답 봉투의 15초 신선도와 따로다.
- **감독은 맞춤 요청을 받은 뒤 `STOP_SYNC_ANSWER_MAX_MS`(5초) 미만에 답을 싣는다.** 받은 때부터 5초가 되면(정각 포함) 답하지 않는다. 그 답은 실행기의 기한 안에 닿는다고 보장할 수 없다(실행기가 이미 버렸는지는 감독이 알 수 없다).
- **맞춤은 정지 해제나 실행 허가가 아니다.** 맞춘 뒤에도 정지 중이면 감독은 시작 지시를 내지 않고, 실행기는 시작 지시가 올 때만 실행을 연다. 정지 해제는 관리자의 CLI 풀기(§7.6)뿐이다.
- **작업 기한은 띄우기 직전에 다시 본다.** 검증은 받은 순간의 시각으로 한 번 본다. 실행기는 준비(폴더, 자격, 격리) 뒤 모델 프로세스를 띄우기 직전에 `deadline_at`과 정지 세대를 다시 확인하고, 지났으면 띄우지 않는다.
- **장부 밖 실행의 세대는 닫는 데만 쓴다.** `hello`·`status_report`로 알게 된 장부 밖 실행을 장부에 실행으로 올리거나 그 결과를 받아들이지 않는다.
- **`ack`는 재전송을 멈추라는 뜻일 뿐이다.** 종료·정리·실행 허가가 아니다.
- **보고가 받아들여진 것은 프로세스 종료의 증명이나 게시 허가가 아니다.** 종료는 종료 확인 영수증으로, 게시는 저장·공개 검사와 현관의 절차로 따로 확인한다.
- **`session_start`의 참조는 감독과 세션 실행기 구현이 대조한다.** `takeover_receipt_id`·`rule_check_id`가 실제로 있는지, 같은 세대인지, 시작 허가가 아직 쓰이지 않았는지는 이 모듈이 보지 않는다(D-50·D-51).
- **자격의 digest는 정확한 자격 바이트로 계산·대조한다.** 문자열 인코딩(UTF-8)과 공백·줄바꿈 처리를 고정해야 같은 값이 같은 digest가 된다. 값은 v1의 메시지에 싣지 않고 v1 밖의 전송 틀(`src/transport/framing.md`의 자격 값 틀)로 온다.
- **메시지 크기 상한(`MAX_MESSAGE_BYTES`)은 이 모듈이 집행하지 않는다.** 바이트 틀이 JSON 해석과 해시 전에 잘라야 한다(중복 키 거절도 같은 자리).
- **주체 이름의 저장소 ID는 실행기의 지속 상태 저장소(Git 저장소가 아님)를 가리킨다.** 저장소가 초기화되면 ID도 바뀌어야 옛 지시가 `wrong_recipient`로 막힌다. ID를 재사용하지 않는다.

### 구현 인수 조건(3차 리뷰)

뒤의 실행기·감독 작업은 위 목록과 아래 조건을 인수 기준으로 쓴다. 아래는 3차 리뷰의 "구현 인수 조건" 가운데 위 목록에 없던 것을 옮긴 것이다.

1. **양쪽 연결 순서.** mTLS 상대와 등록된 Ed25519 키·역할·인스턴스·저장소 ID를 결합한다. 감독은 그 연결의 요청을 딱 한 번 검증하고 그 송신자에게만 답한다. 양쪽 모두 맞춤을 생략한 `hello`, 같은 연결의 두 번째 맞춤, `hello` 뒤 맞춤을 처리하지 않는다. 새 연결이 열리거나 기존 연결이 닫히면 이전 대기값과 비동기 처리 결과도 폐기한다.
2. **재생과 과부하.** 실행기는 암호학적 난수로 매 연결 16바이트를 생성한다. nonce 소비는 동시성·재시작에도 한 번만 성공해야 한다. 반복 재접속·인증 주체별 요청 빈도 및 동시 처리 제한은 이 계약에 명시돼 있지 않으므로, 감독 구현에서 반복 요청이 서명·저장을 무한히 유발하지 않는지 확인한다.
3. **복원·저장·경합.** 감독은 단일 작성자 잠금과 최신 정지 원장 복원 전에는 맞춤·일반 발급을 닫고, 답을 서명하는 시점의 권위 세대를 사용한다. 실행기는 `0`도 저장한다. 적용 시점에 현재 세대와 연결을 다시 확인한다. 동시 정지나 저장 실패 시 연결을 닫고, 진행 중인 안전한 종료는 계속한다. 큰 오발급 복구 시 기존 저장소 ID를 폐기하고 새 ID를 인증에 다시 묶는다.
4. **정지와 허가.** 복원·맞춤·`hello`는 시작, 자격 발급, 기존 실행 갱신, 정지 완료의 증거가 될 수 없다(맞춤 성공을 접수 재개나 자격 부여로 연결하지 않는다). 정지 중과 CLI 풀기 완료 전에는 접수·발급을 닫고, 실행 직전에 세대·기한·시작 허가를 다시 확인한다. 종료를 놓친 실행과 장부 밖 실행은 점유를 대조한다. 옛 실행을 되살리거나 결과를 승격시키지 않는다. D-38·D-39의 정지 확인과 풀기는 관리자 CLI에 둔다.

## 정하지 않은 것

내는 쪽 기본값과 운영 숫자(갱신 10초, 끊김 30초, 전달 상한 10초, 맞춤 수명의 내는 쪽 기본값 15초 `STOP_SYNC_TTL_MS`, 감독의 맞춤 처리 상한 5초 등)는 기본값(관리자 미확정)이다(`limits.ts`). 받는 쪽 경계(수명 상한 30초·15초, 시계 오차 1초, 맞춤 대기 25초, 임대 상한 30초, 크기·개수·결과 상한)는 v1에 고정이고, 기본값은 그 경계 안에서만 바꾼다(README "판 규칙"). 이름에 `MAX`가 든 전달 상한·감독의 맞춤 처리 상한·준비 상한은 받는 쪽이 검사하지 않는 기본값이다. 감독의 끊김 판정(`DISCONNECT_JUDGE_MS`)은 v1에서 더 길게(예: 60초) 바꿀 수 있고, 갱신 없는 단일 임대(`run_renew`의 `lease_until`)는 v1에서 발급 뒤 30초까지다. 임대를 더 길게 하려면 판을 올린다. 세션 파드의 기동 실패 한도와 `hold`의 모양, 올리브 자신의 경보 목록, 제어 컨테이너의 건강 확인·지표 포트는 값을 두지 않았다. 바이트 틀(길이 접두, 중복 키 거절)과 자격 값을 나르는 틀은 v1 밖의 전송 모듈(`src/transport/framing.ts`)에 있다. 감독이 값을 보내는 규칙과 실행기가 받는 규칙은 뒤 작업이다. 현관과 감독 사이의 동작(§9.1)은 v1에 없다.
