# olive-control/v1 요약

감독, 실행기, 현관이 함께 쓰는 계약이다. 코드는 `src/contract/v1/`(공개 면은 `index.ts`), 사례는 `contracts/fixtures/v1/`. 설계의 기준은 homelab `docs/plans/2026-11-13-olive/supervisor.md` §9다. 표와 코드가 다르면 코드가 맞고, 이 표를 고친다.

## 봉투

연결 위의 메시지는 모두 `{ header, signature, body }`다. 세 칸 밖의 칸, 머리·본문의 모르는 칸은 거절한다.

| 머리 칸 | 값 |
|---|---|
| `contract` | `"olive-control/v1"` |
| `sender`, `recipient` | `supervisor`, `front-door`, `executor/<session\|역할>/<인스턴스>/<저장소>` |
| `action` | 아래 19개 |
| `request_id` | 소문자 UUID |
| `stop_generation` | 정지 세대(0 이상 정수). 받는 쪽의 값과 같아야 한다. 예외는 아래 "정지 세대 올리기" 하나 |
| `run_generation` | 본문이 가리키는 실행의 세대. 실행에 묶이지 않는 메시지는 0 |
| `body_digest` | 본문 정규 직렬화의 SHA-256, 소문자 16진 |
| `issued_at`, `expires_at` | Unix epoch 밀리초. 수명은 0 초과 30초 이하 |
| `nonce` | 소문자 16진 32자. 낸 쪽마다 한 번 |

**서명 대상:** `header` 전체의 정규 직렬화를 UTF-8로 쓴 바이트. Ed25519, base64url(패딩 없음, 86자). 다시 써서 같은 표기만 받는다.

**정규 직렬화:** RFC 8785(JCS)의 부분집합. 키는 UTF-16 코드 단위 순서, 공백 없음, 문자열은 JCS 이스케이프. 숫자는 안전 정수만(소수·지수 없음, `-0`은 `0`). 짝 없는 서로게이트, 깊이 16 초과는 받지 않는다. 받는 쪽은 받은 바이트가 아니라 해석한 값으로 다시 만들어 서명을 확인한다.

**검증 순서:** 모양(봉투 → 계약 판 → 동작 → 머리) → 서명 → 방향 → 받는 쪽 → 시한 → 본문(digest → 금지 칸 → 모양 → 관계 → 받는 시각 기준의 관계) → 정지 세대 → 상태 목록의 실행 세대 → 실행 세대 → nonce. 이유는 `envelope.ts`의 `verifyEnvelope` 주석에 있다. nonce는 받아들일 봉투만 쓴다.

**결과:** 통과하면 `{ ok: true, action, header, body, sender, recipient, adoptedStopGeneration }`, 거절이면 `{ ok: false, reason }`(사유 하나). `adoptedStopGeneration`은 이 봉투로 받는 쪽의 정지 세대가 올라갔으면 그 값, 아니면 `null`이다. fixture의 `expect`도 같은 값을 `adopted_stop_generation`으로 적는다.

## 정지 세대 올리기

비상 정지(supervisor.md §7.3)는 감독이 새 정지 세대를 적용하고, 권한을 끊고, 실행기에 종료를 지시하는 순서다. 그 종료 지시가 새 세대를 실행기에 옮긴다.

- **더 높은 정지 세대를 받아들이는 동작은 둘뿐이다:** `reason: "emergency_stop"`인 `task_cancel`과 `session_stop`. 나머지 모든 동작(시작·갱신·확정, 다른 사유의 종료·취소, 영수증·보고·전송, 감독 쪽에서 받는 모든 것)은 지금처럼 정확히 같아야 한다.
- **세대는 내려가지 않는다.** 받는 쪽보다 낮은 값은 비상 종료여도 거절한다. 새 세대를 받아들인 뒤에는 옛 세대의 시작·갱신이 서명과 시한이 맞아도 `stop_generation_mismatch`다.
- **왜 종료 지시인가:** 설계의 순서가 "감독이 종료를 지시한다"이고, 지시의 종류는 여섯뿐이다(§9.2). 따로 세대 동기화 메시지를 두면 효과를 내는 메시지가 하나 늘어난다. 종료는 실행을 닫기만 하므로 미래 세대를 받아도 새로 열리는 것이 없다.
- **한계:** 받는 쪽이 아는 실행을 닫는 지시라서(`unknown_run`은 그대로), **쥔 실행이 없는 실행기는 이 길로 새 세대를 알 수 없다.** 감독이 내려가 있어 §7.3의 4단계를 건너뛴 경우도 같다. 그런 실행기는 옛 세대로 남고, 감독의 새 세대 지시를 모두 거절하며, 감독도 그 실행기의 옛 세대 `hello`를 거절한다. 그런 실행기는 §7.3의 replicas 0과 §7.6의 풀기로 내려갔다 올라와야 하는데, 다시 뜬 실행기가 지금의 정지 세대를 어디서 받는지는 계약에 없다(아래 "구현이 지킬 것"과 "정하지 않은 것").

## 받을 때만 보는 관계

본문 해석기는 `receivedAt`(받는 쪽의 지금 시각)을 받는다. 봉투를 만들 때(`sealEnvelope`)는 `null`이라 발급 시각 기준의 관계만 본다.

- `task_start.deadline_at`: 만들 때는 `issued_at`보다 커야 한다(아니면 `body_malformed`). 받을 때는 받는 시각보다 커야 한다. 같거나 이르면 `deadline_passed`다. 봉투의 30초 시한과 작업 기한은 따로다.

## 지시(감독 → 실행기), 이 여섯뿐

| 동작 | 받는 쪽 | 본문 |
|---|---|---|
| `session_start` | 세션 | `run_id`, `generation_marker_digest`, `takeover_receipt_id`(첫 세션이면 null), `rule_check_id`, `profile_revision`, `policy_revision`, `handoff_digest`, `credential` |
| `session_stop` | 세션 | `run_id`, `reason`(daily_rotation, session_broken, emergency_stop, account_switch) |
| `task_start` | 작업자 | `run_id`, `role`(실행기의 역할과 같아야 함), revision 둘, `snapshot_digest`, `input_digest`, `deadline_at`, `budget_tokens`, `credential` |
| `task_cancel` | 작업자 | `run_id`, `reason`(requested, deadline, budget, emergency_stop) |
| `run_renew` | 둘 다 | `run_id`, `lease_until`(발급 뒤 30초 안) |
| `result_finalize` | 작업자 | `run_id`, `outcome`, `result_digest`(succeeded일 때만), `stored_at` |

`credential`은 자격의 값이 아니라 `account`, `method`, `revision`, `digest`(값의 SHA-256)다. 명령·이미지·볼륨·argv·환경(과 그 변형 이름)의 칸은 어느 깊이에 있든 `forbidden_field`다.

## 영수증·보고(실행기 → 감독)

| 동작 | 내는 쪽 | 본문의 요지 |
|---|---|---|
| `receipt_accepted` | 둘 다 | `receipt_id`, `run_id`, `instruction_request_id`, `instruction` |
| `receipt_started` | 둘 다 | `receipt_id`, `run_id`, `instruction_request_id`, `started_at` |
| `receipt_stopped` | 작업자 | `remaining_processes: 0`, `exit`, `stopped_at` |
| `receipt_cleaned` | 작업자 | `instruction_request_id`(결과 확정), `cleaned_at` |
| `receipt_session_takeover` | 세션 | `previous_run_id`, `new_generation_marker_digest`, `start_permit_id`(셋 다 필수, D-50), `taken_over_at` |
| `report_session_broken` | 세션 | `cause`(main_exited, main_restarted_alone, relay_lost), `generation_marker_digest`(D-52) |
| `report_rule_check` | 세션 | `outcome`, 재시작 전후 표식 digest, `start_permit_id`(D-51) |
| `report_hook_event` | 세션 | `session_id`, `prompt_id`(둘 다 필수), `event`, `error`(StopFailure일 때만) |
| `report_result` | 작업자 | `result`: `role`, `outcome`, `summary`, `items`, `refs`. 정규 직렬화 16KiB 이하. 로그·사고 과정 칸 없음 |

같은 영수증·보고는 같은 `receipt_id`·`report_id`와 같은 `body_digest`다. 다시 보낼 때는 같은 본문을 새 봉투에 담는다.

## 전송(D-55)

| 동작 | 방향 | 본문 |
|---|---|---|
| `hello` | 실행기 → 감독 | revision 둘, 쥔 실행의 상태, 받음 확인 못 받은 id |
| `status_query` | 감독 → 실행기 | `run_ids`(이미 있는 실행 ID만, 1~8개) |
| `status_report` | 실행기 → 감독 | `in_reply_to`, 실행 상태 |
| `ack` | 감독 → 실행기 | 반영한 영수증·보고 id |

**실행 상태 항목**(`hello`·`status_report`의 `runs[]`): `run_id`, `state`, `run_generation`, `last_receipt_id`. 같은 `run_id`는 한 메시지에 한 번만 온다.

- `run_generation`은 실행기 장부에 적힌 그 실행의 세대다(서명된 본문 안). `not_known`(실행기에 기록이 없음)이면 `run_generation`과 `last_receipt_id`는 `null`이고, 그 밖의 상태면 `run_generation`은 1 이상이다.
- **감독이 아는 실행**이면 감독 장부의 세대와 같아야 한다. 다르면 봉투째 `run_generation_mismatch`다(옛 세대의 늦게 온 상태).
- **감독이 모르는 실행**(장부 밖)이면 통과한다. 그 세대는 재개나 결과 반영의 권한이 아니다. 그 실행을 닫는 지시(`task_cancel`·`session_stop`의 `run_generation`)와 `status_query`의 대조에만 쓴다. `runsOutsideLedger`가 그런 항목을 고른다(supervisor.md §8의 2).

연결이 살아 있지 않으면 지시를 만들지 않는다(`no_connection`). 남은 시한이 전달 지연 상한(10초, 기본값)보다 짧은 봉투는 싣지 않는다(`too_late_to_send`). 끊김 판정 뒤 끝났다고 증명되지 않은 실행은 `unknown_running`이다. 다시 붙으면 같은 실행 ID를 묻기만 하고 새 실행 ID로 다시 보내지 않는다.

## 거절 사유

`malformed`, `unknown_field`, `contract_mismatch`, `unknown_action`, `unknown_sender`, `bad_signature`, `wrong_direction`, `wrong_recipient`, `lifetime_invalid`, `not_yet_valid`, `expired`, `body_malformed`, `digest_mismatch`, `forbidden_field`, `role_mismatch`, `result_too_large`, `deadline_passed`, `stop_generation_mismatch`, `unknown_run`, `run_generation_mismatch`, `replayed`. 전송 규칙: `no_connection`, `too_late_to_send`, `receipt_conflict`.

## 구현이 지킬 것

이 모듈은 받아도 되는 메시지인지만 가른다. 아래는 감독·실행기 구현이 지켜야 계약의 보호가 성립하는 것이다.

- **새 정지 세대의 적용은 실행기의 일이다.** `adoptedStopGeneration`이 null이 아니면, 그 봉투의 효과(종료)를 내기 전에 새 세대를 지속 상태 저장소에 적고 그보다 낮은 세대의 지시로 새 실행이 열리지 않게 막는 일을 한 번에(원자적으로) 한다. 적지 못했으면 종료는 하되 새 지시를 받지 않는다.
- **다시 뜬 실행기의 정지 세대.** 쥔 실행이 없어 비상 종료를 받지 못한 실행기, 감독이 없어 종료가 오지 않은 실행기가 지금의 정지 세대를 어떻게 받는지는 이 계약이 정하지 않았다. 뒤 작업이 정한다(실행기를 띄우는 쪽이 지금의 세대를 주거나, 감독과의 인증된 세대 맞춤 절차를 v2에 더하는 등). 그 전에는 옛 세대 실행기와 감독 사이의 모든 메시지가 `stop_generation_mismatch`로 막힌다(안전한 쪽으로 막힘).
- **작업 기한은 띄우기 직전에 다시 본다.** 검증은 받은 순간의 시각으로 한 번 본다. 실행기는 준비(폴더, 자격, 격리) 뒤 모델 프로세스를 띄우기 직전에 `deadline_at`과 정지 세대를 다시 확인하고, 지났으면 띄우지 않는다.
- **장부 밖 실행의 세대는 닫는 데만 쓴다.** `hello`·`status_report`로 알게 된 장부 밖 실행을 장부에 실행으로 올리거나 그 결과를 받아들이지 않는다.
- **`ack`는 재전송을 멈추라는 뜻일 뿐이다.** 종료·정리·실행 허가가 아니다.
- **보고가 받아들여진 것은 프로세스 종료의 증명이나 게시 허가가 아니다.** 종료는 종료 확인 영수증으로, 게시는 저장·공개 검사와 현관의 절차로 따로 확인한다.
- **`session_start`의 참조는 감독과 세션 실행기 구현이 대조한다.** `takeover_receipt_id`·`rule_check_id`가 실제로 있는지, 같은 세대인지, 시작 허가가 아직 쓰이지 않았는지는 이 모듈이 보지 않는다(D-50·D-51).
- **자격의 digest는 정확한 자격 바이트로 계산·대조한다.** 문자열 인코딩(UTF-8)과 공백·줄바꿈 처리를 고정해야 같은 값이 같은 digest가 된다. 값을 나르는 메시지는 아직 없다.
- **메시지 크기 상한(`MAX_MESSAGE_BYTES`)은 이 모듈이 집행하지 않는다.** 바이트 틀이 JSON 해석과 해시 전에 잘라야 한다(중복 키 거절도 같은 자리).
- **주체 이름의 저장소 ID는 실행기의 지속 상태 저장소(Git 저장소가 아님)를 가리킨다.** 저장소가 초기화되면 ID도 바뀌어야 옛 지시가 `wrong_recipient`로 막힌다. ID를 재사용하지 않는다.

## 정하지 않은 것

시간 숫자(갱신 10초, 끊김 30초, 전달 상한 10초 등)는 기본값(관리자 미확정)이다(`limits.ts`). 세션 파드의 기동 실패 한도와 `hold`의 모양, 올리브 자신의 경보 목록, 제어 컨테이너의 건강 확인·지표 포트는 값을 두지 않았다. 자격 값을 나르는 메시지의 모양과 바이트 틀(길이 접두, 중복 키 거절)은 뒤 작업이다. 현관과 감독 사이의 동작(§9.1)은 v1에 없다. 쥔 실행이 없는 실행기와 다시 뜬 실행기가 지금의 정지 세대를 받는 길도 정하지 않았다(위 "구현이 지킬 것").
