# 연결 상실 반영의 한 박자 (`link-loss.ts`)

배정기 순환의 한 박자다. 장부에 종료가 확인되지 않은 실행을 쥔 작업자 실행기마다, **그 실행기의 인정된 연결이 없는 채로 끊김 판정 시간을 넘겼을 때만** 끊겼다고 보고 장부의 `markLostFor`를 그 실행기의 주체 이름으로 한 번 부른다. 끊긴 시간은 **단조 시계로만** 잰다(벽시계의 보정을 끊긴 시간으로 세지 않는다). 옮긴 실행은 `unknown_running`이 되고 자리를 쥔 채다. 이 박자는 자리를 풀지도, 실행을 끝난 상태로 옮기지도 않는다. 장부·연결 표·정지 세대·시계 둘은 포트로, 판정 시간은 정책으로, 앞 박자들이 본 연결의 기억은 인자로 받는다. 소켓·타이머·시계를 직접 부르지 않는다(시험이 소스를 읽어 지킨다).

박자 안에 `await`가 없다(함수가 동기다). 연결 표를 읽은 뒤 장부에 쓰기까지 소켓 사건이 끼어들 수 없으므로, 판정과 쓰기 사이에 다시 붙은 연결을 놓치지 않는다.

## 공개 면

```ts
linkLossTick(ports: LinkLossPorts, policy: LinkLossPolicy, input: LinkLossTickInput): LinkLossTickResult

LinkLossPorts = {
  ledger: Pick<Ledger, "listRuns" | "markLostFor">
  connections: Pick<Connections, "occupancy">   // 부르는 쪽이 쥔 지금의 연결 표
  restorer: StopGenerationSource                // 연결 표의 step에 넘기는 바로 그 복원기 객체
  clock: Clock                                  // ports.ts. 장부 시계와 같은 벽시계. markLostFor의 now와 결과의 at에만 쓴다
  monotonic: MonotonicClock                     // { now(): number }. 끊긴 시간을 재는 단조 시계(0 이상의 안전 정수 ms)
  beatValid?: () => boolean                     // 박자 유효 문. 실행기마다 markLostFor 바로 앞. 빠지면 늘 유효(조립은 반드시 넘긴다)
}
LinkLossPolicy = { judgeMs: number }           // RUN_LEASE_MAX_MS 이상의 안전 정수
LinkLossTickInput = { watch: WatchEntry[] }    // 앞 박자의 결과 watch 그대로
WatchEntry = { executorId: string, absentSince: number | null }   // 작업자 실행기 주체 이름, 단조 시각(0 포함) 또는 null

LinkLossTickResult =
  | { kind: "not_run", reason: "clock_unavailable" | "input_malformed" | "policy_rejected" | "tick_in_progress" | "links_unknown" | "read_unknown" }
  | { kind: "ran", executors: ExecutorOutcome[], watch: WatchEntry[], halted: "threw" | null, haltedAt: string | null }
```

| 실행기마다 (`ExecutorOutcome`) | 뜻 |
|---|---|
| `linked` | 인정된 연결이 있다 |
| `within_judge` + `absentSince` | 연결이 없지만 판정 시간 안이다(정각 포함). `absentSince`는 단조 시각이다 |
| `unknown` + `reason` | 판정하지 않았다: `never_seen`(이 프로세스가 그 연결을 본 적이 없다), `clock_regressed`(단조 시계가 `absentSince`보다 이르다), `read_unknown`(그 실행기의 실행 줄의 꼴이 틀리다) |
| `not_worker` | 세션 실행기. 연결 표가 세션 실행기의 연결을 아직 인정하지 않는다(맞춤 요청은 작업자 주체만 받는다) |
| `moved` + `absentSince`, `at`, `runs` | `markLostFor`가 옮겼다. `runs`는 장부의 답(`runId`, `runGeneration`, `before`, `after`)이고 `before`는 진행 중 상태(`preparing`·`running`·`stopping`), `after`는 `unknown_running`이다. 빈 목록이면 부르는 순간 옮길 실행이 없었다. `at`은 장부에 넘긴 벽시계 시각이다 |
| `beat_closed` + `absentSince` | `markLostFor` 바로 앞에서 본 박자 유효 문이 닫혔다. 부르지 않았다 |
| `ledger_failed` + `absentSince`, `reason` | 옮김으로 세지 않는다. 장부의 거절 이름(`ledger_unwritable` 등), `threw`(장부 포트가 던짐), `malformed_answer`(답이 정의 밖). 뒤의 둘은 옮겼는지 모른다 |

결과의 항목은 종료가 확인되지 않은 실행(`preparing`·`running`·`stopping`이고 `stopReceiptId`가 없음)을 쥔 실행기와 실행 줄의 꼴이 틀린 실행기만이고, 주체 이름 순이다. 결과에는 원문·자격·봉투가 없다.

## 판정의 입력: "마지막으로 인정된 연결"을 어디서 얻는가

- **인정된 연결은 연결 표의 `occupancy(restorer)`에 그 주체 이름이 있는 것이다.** 맞춤과 인사를 지금의 복원기로 마치고 아직 열린 연결이다(`connections.ts`의 `#greetedNow`). 행의 `executorId`가 맞춤 요청을 서명한 주체 이름 그대로라 장부의 지정 실행기와 정확히 같은 문자열로 대조한다. `candidates`는 주체 이름 문자열을 싣지 않아 쓰지 않았다. 같은 집합이다. 행의 이름이 작업자 실행기 주체(계약 v1의 `parsePrincipal`)로 읽히지 않으면 표 전체를 모름(`links_unknown`)으로 둔다. 그런 표를 다른 실행기가 없다는 증거로 쓰지 않는다.
- **언제부터 없었는가는 부르는 쪽의 메모리(`watch`)로 넘긴다.** 연결 표는 연결이 사라진 시각을 남기지 않는다(닫힌 연결의 행을 지운다). 그래서 박자가 결과로 다음 기억을 내고, 부르는 쪽은 그것을 다음 박자에 그대로 넘긴다(수명 박자의 `lastQueries`와 같은 방식).
  - `absentSince: null`: 마지막 박자에 인정된 연결이 있었다.
  - `absentSince: t`: 연결을 본 뒤 단조 시각 `t`의 박자에 처음으로 없음을 확인했다. `t`는 0일 수 있다.
  - 기억에 없음: 이 프로세스가 그 실행기의 연결을 본 적이 없다.
- **조회만으로는 두 박자 사이의 재인정을 알 수 없다.** 박자는 부르는 순간의 표만 본다. 두 박자 사이에 다시 붙었다가 다시 끊긴 실행기는 기억에 옛 `absentSince`가 남아 그 시각부터 센다(판정이 이르게 된다). 그래서 이 설명 전체는 **부르는 쪽이 연결 표의 `candidate`마다 기억에 `null`을 더한다**는 전제 위에 선다(아래 "뒤 조각이 지킬 것").
- **없음을 세는 시작은 "처음 없음을 확인한 박자의 단조 시각"이다.** 연결이 실제로 사라진 순간보다 이르지 않으므로 센 경과는 실제 경과보다 길지 않다. 판정은 늦을 수 있어도 이르지 않다. 늦어지는 폭은 박자 간격 둘까지다: 사라진 뒤 처음 없음을 보는 데 한 간격, 판정 시간의 정각을 넘긴 것을 확인하는 데 한 간격이 들 수 있다(정수 시각 기준. 아래 "D-89의 한계에서 이 박자가 줄이는 것"의 조건부 상한과 같은 말이다). 경과는 단조 시계로만 재므로 벽시계가 앞으로 보정돼도 끊긴 시간이 늘지 않는다.
- **본 적 없는 실행기는 판정하지 않는다(`never_seen`).** 감독이 막 떴으면 기억이 비어 있다. 재시작 뒤의 대조는 복원의 몫이다(복원 3단계가 진행 중 실행을 `unknown_running`으로 옮긴다).
- **기억을 넘기지 않은 결과는 셋으로 갈린다.** `watch` 칸이 없는 입력(`{}`)은 `not_run`(`input_malformed`)이다. `{ watch: [] }`이면 인정되지 않은 실행기는 `unknown`(`never_seen`)이고, 인정된 실행기는 `linked`이며 그 이름이 다음 기억에 `null`로 들어간다.
- **기억에는 실행을 쥐지 않은 실행기도 담는다.** 박자 사이에 배정·시작된 뒤 끊긴 실행기를 `never_seen`으로 놓치지 않기 위해서다. 크기는 이 프로세스가 본 주체 수로 묶인다(등록표가 믿은 주체뿐).
- **기억의 이름은 작업자 실행기 주체여야 한다.** 하나라도 아니면(빈 문자열, 세션 실행기, 꼴이 아닌 이름) 기억 전체가 `input_malformed`이다.
- **같은 실행기의 기억이 둘 이상이면 판정이 늦어지는 쪽으로 합친다:** `null`이 있으면 `null`, 아니면 더 늦은 시각이다.

## 한 박자의 순서

1. **전제.** 같은 장부 포트로 진행 중인 박자가 없음(`tick_in_progress`), 정책(`judgeMs`가 `RUN_LEASE_MAX_MS` 이상의 안전 정수, 아니면 `policy_rejected`), 기억의 꼴(`input_malformed`), 시계 둘(벽시계는 양의 안전 정수, 단조 시계는 0 이상의 안전 정수. 하나라도 읽지 못하면 `clock_unavailable`), 연결 표(`links_unknown`), 실행 목록(`read_unknown`). 하나라도 모름이면 `not_run`이고 아무것도 쓰지 않는다. 부르는 쪽은 앞 기억을 그대로 쥔다.
2. **연결 표.** 복원기의 세대가 0 이상의 안전 정수가 아니면(모름) `links_unknown`이다. 세대를 모르는 연결 표는 아무도 인정하지 않으므로, 그 답을 "모두 끊김"으로 읽지 않는다. 연결 표는 조회 안에서 세대를 다시 읽고 모르면 빈 목록을 내므로, **표를 읽은 뒤 세대를 다시 읽어** 여전히 알려져 있고 처음 읽은 값과 같지 않으면 `links_unknown`이다. 이 다시 읽기가 잡는 것은 표 조회 안의 세대 읽기 실패가 **같은 박자의 마지막 읽기까지 유지될 때**뿐이다(같은 복원기 객체에서 세대 읽기의 실패가 한 박자 안에 풀리지 않는다는 조건. 실제 복원기는 장부가 실패하면 다시 열어 복원할 때까지 `null`이라 이 조건을 지킨다). 표 조회 안의 읽기만 실패하고 앞뒤 읽기는 같은 값을 내는 복원기에서는 살아 있는 연결이 빈 표로 보여 그 실행기의 없음을 세기 시작하고, 그런 박자가 판정 시간을 넘겨 이어지면 살아 있는 실행을 옮긴다. 행이 배열이 아니거나 행의 `executorId`가 작업자 실행기 주체가 아니면, 또는 읽다 던지면 `links_unknown`이다.
3. **실행 목록.** 목록의 원소를 꺼내다 던지거나 어느 실행기의 줄인지 모르는 줄(지정 실행기를 읽지 못함)이 하나라도 있으면 `read_unknown`이다. 실행기는 알지만 종류·상태·종료 확인 칸의 꼴이 틀리거나 종류와 주체가 맞지 않는 줄(작업자 실행인데 세션 실행기 이름 등)이 있으면 그 실행기만 `unknown`(`read_unknown`)이다.
4. **다음 기억을 만든다.** 쓰기와 무관하게 이 자리에서 만들므로 멈춰도 온전하다. 처음 없음을 확인한 실행기에는 이번 박자의 단조 시각을 적는다.
5. **실행기마다(이름 순) 판정한다.** 연결 있음 → `linked`. 본 적 없음 → `never_seen`. 단조 시계가 `absentSince`보다 이름 → `clock_regressed`. `단조 시각 − absentSince <= judgeMs` → `within_judge`. 넘겼으면 `markLostFor({ executorId, now: 벽시계 })`를 한 번 부른다.

## 경계

- **정각은 아직이다.** `단조 시각 − absentSince`가 `judgeMs`와 같으면 `within_judge`이고 1ms 넘겨야 옮긴다. 계약 v1의 `viewLink`는 정각부터 `lost`다(`>=`). 이 박자는 1ms 늦은 쪽(살아 있는 실행을 옮기지 않는 쪽)을 골랐다.
- **단조 시계가 `absentSince`보다 뒤로 가면 모름이다.** 지금 읽은 단조 시각이 처음 없음을 확인한 시각(`absentSince`)보다 이르면 경과를 모르므로 판정하지 않고, 기억은 그대로 넘긴다. 박자가 알아채는 후퇴는 이것뿐이다. 직전 박자의 값보다만 이르고 `absentSince` 이후인 값은 알아채지 못하고 그 값으로 경과를 재므로, 그 값이 판정 시간을 넘기면 옮긴다. 그래서 단조 시계 포트는 후퇴하지 않아야 한다(한 프로세스 안의 단조 시계는 뒤로 가지 않으므로, 후퇴는 다른 프로세스의 기억을 넘겼거나 포트가 어긋난 경우다).
- **벽시계는 경과에 쓰지 않는다.** 벽시계가 앞이나 뒤로 보정돼도 판정은 바뀌지 않는다. 벽시계는 장부에 넘기는 `now`와 결과의 `at`에만 쓴다.
- **판정 시간은 `RUN_LEASE_MAX_MS` 이상만 받는다.** 판정할 때 실행기는 갱신 없이 임대가 끝나 이미 닫혀 있어야 한다(`limits.ts`의 `DISCONNECT_JUDGE_MS` 주석). 더 짧은 값은 `policy_rejected`이다. 기본값은 계약의 `DISCONNECT_JUDGE_MS`(관리자 미확정)이고 이 모듈은 숫자를 두지 않는다. 조립이 넘긴다.

## 장부 쓰기와 실패

- **그 실행기의 정확한 이름으로 한 번만.** 연결 표의 주체 이름과 장부의 지정 실행기를 문자열로 대조한다. 저장소 ID만 다른 이름도 다른 실행기다. `markLost`(전부 옮기기)는 포트에 없다.
- **부르기 바로 앞에서 박자 유효 문을 본다.** 앞 실행기의 장부 쓰기 안에서 박자 기한이 지났을 수 있으므로 실행기마다 장부 포트 객체를 얻은 뒤 `markLostFor` 바로 앞에서 선택 포트 `beatValid`를 본다(포트 객체의 접근자가 유효 문 뒤에 돌지 않게). 그 칸은 부를 때마다 한 번 읽고 포트 묶음을 수신자로 부른다(`send-gate.ts`의 `holdBeatValid`). `true`가 아니거나 던지면 그 실행기는 부르지 않고 `beat_closed`(+ `absentSince`)이며 기억은 그대로 넘어간다. 그 차례(장부 포트 객체·메서드·인자 → 유효 문 → 호출)는 `send-gate.ts`의 `callAfterGate`가 한다. 포트가 빠지면 늘 유효다(이 부품 단독의 쓰임).
- **장부의 거절은 그 이름 그대로 `ledger_failed`이다.** 기억의 `absentSince`는 남는다. 다음 박자가 실제로 다시 부르는지는 장부와 복원기의 상태에 달렸다.
  - 장부가 건강한 채 거절만 돌려준 경우: 다음 박자가 다시 판정해 다시 부른다.
  - **실제 장부의 쓰기가 실패한 경우:** 장부는 실패 상태에 들어가고, 부르는 쪽은 장부를 다시 열어 복원하는 경로로 보낸다. 그 뒤 이 박자의 동작은 세 단계로 갈린다(복원기의 세대는 `src/ledger/restore.ts`의 `stopGeneration`).
    1. **실패 상태의 장부:** 그 장부의 복원기는 세대가 `null`이다. 이 박자는 `links_unknown`으로 돌고 쓰지 않는다. 부르는 쪽은 앞 기억을 쥔다.
    2. **다시 연 뒤 새 복원기의 1단계 전:** 새 복원기도 세대가 `null`이라 `links_unknown`이고 쓰지 않는다.
    3. **새 복원기의 1단계 뒤:** 세대가 다시 알려진다. **복원의 2~5단계가 끝나지 않았어도(뒤 단계가 실패해 멈춰 있어도) 이 박자는 돌고, 판정 시간을 넘긴 실행기를 옮길 수 있다.** 접수가 닫혀 있는지는 이 박자가 보지 않는다.
    복원이 끝나기 전의 박자를 막으려면 조립이 그동안 이 박자를 부르지 않아야 한다(아래 "뒤 조각이 지킬 것").
  - `markLostFor`의 쓰기 모드는 `continue`라 장부가 "못 씀"이어도 시도하고, 닫힌 장부는 `ledger_unwritable`이다(`src/ledger/ledger.md` "실행기 하나의 끊김").
- **던짐·정의 밖의 답은 옮겼는지 모른다.** 다시 불러도 이미 옮긴 실행은 집합 밖이라 세지 않으므로 다음 박자의 다시 부르기는 해롭지 않다. 다만 그때 답의 목록은 비어 있을 수 있다. 옮긴 실행은 장부의 `unknown_running`으로 찾는다.
- **답의 실행 목록은 칸마다 한 번 읽어 옮겨 적는다.** 하나라도 꼴이 틀리면(실행 ID가 UUID가 아님, 실행 세대가 양의 안전 정수가 아님(장부의 실행 세대는 1부터), `before`가 진행 중 상태가 아님, `after`가 `unknown_running`이 아님) `malformed_answer`다. `markLostFor`가 할 수 없는 전이를 옮김으로 세지 않는다. 진행 중 상태는 장부의 전이표(`TRANSITIONS`)에서 `unknown_running`으로 갈 수 있는 상태로 고른다(장부의 `#moveLost`가 고르는 집합과 같다).

## 자리와 임대

이 박자는 장부에 `markLostFor` 말고 쓰지 않는다. 연결의 끊김이나 `withdrawn`·`close`는 종료의 증거가 아니라서 자리를 푸는 근거로 쓰지 않는다. 옮긴 실행은 `unknown_running`이고 자리를 쥔 채이며 같은 종류의 새 시작은 `slot_busy`다. 그 뒤 수명 판단(`nextIntent`)은 믿은 임대가 남아 있어도 갱신을 내지 않고(취소·기한이 없으면 같은 실행 ID의 조회), 장부도 갱신 기록을 `transition_denied`로 거절한다(시험이 실제 장부로 본다). D-92에 따라 다시 붙은 실행기가 "아직 돈다"고 답해도 그 실행을 되살리지 않는다.

## 겹쳐 부르기

같은 장부 포트 객체로 박자가 진행 중이면 읽기·쓰기 없이 `tick_in_progress`다. 박자가 동기라 겹치는 길은 포트 안에서 다시 부르는 것뿐이다. 다른 포트 객체로 같은 장부를 부르는 다른 경로(복원의 `markLost` 등)와의 순서는 부르는 쪽이 정한다. 같은 실행을 두 번 옮기지는 않는다(장부의 집합이 막는다).

## 박자가 멈출 때

- **포트의 예외는 그 실행기의 결과다.** `markLostFor`가 던지면 `ledger_failed`(`threw`)이고 다음 실행기를 본다.
- **장부 쓰기를 부른 뒤 답을 읽다 던지면**(답의 칸 getter 등) 그 실행기를 `ledger_failed`(`malformed_answer`)로 싣고 남은 실행기를 하지 않고 `halted: "threw"`, `haltedAt`은 그 실행기다. 그 전까지의 결과와 다음 기억은 그대로다. 부르는 쪽은 장부를 다시 읽어 멈춘 실행기와 결과에 없는 실행기를 대조한다.

## D-89의 한계에서 이 박자가 줄이는 것

D-89는 "실행기의 종료 소식을 장부까지 잇는 조각(영수증 처리기, 연결 끊김 반영)이 생기기 전에는 감독이 믿는 끝과 실제의 어긋남에 상한이 없다"고 적었다. 이 박자가 붙으면 인정된 연결이 사라진 실행기의 진행 중 실행은 사라진 순간부터 `judgeMs` + 박자 간격 두 번 안에 `unknown_running`이 되고 그 뒤 갱신이 적히지 않는다(처음 없음을 보는 데 한 간격, 정각을 넘긴 것을 확인하는 데 한 간격. 단조 시계의 정수 시각 기준이다). **이 상한은 연속된 단절에서 박자 간격이 지켜지고, 그동안 세대·연결 표·장부의 읽기와 장부의 쓰기가 성공할 때만 선다.** 장부가 실패 상태이거나 읽기가 계속 모름이면 이 박자는 쓰지 않으므로 상한이 없다. 아래 "남는 한계"의 조건 밖에서만 선다.

## 남는 한계

- **열려 있지만 조용한 연결은 살아 있는 것으로 본다.** 이 박자는 연결 표가 인정하는지만 보고, 계약 v1의 `viewLink`처럼 마지막 수신 시각으로 `lost`를 내지 않는다. 연결 표에 마지막 수신 시각이 없기 때문이다. 상대가 사라졌는데 소켓이 닫힘을 알리지 않는(반쯤 열린) 연결은 닫힐 때까지 인정된 연결로 남고, 그동안 이 박자는 옮기지 않는다. 감독 서버가 TCP keepalive로 그런 연결을 운영체제 기한(첫 탐침 지연 30초 + 탐침 간격 10초 × 4회, 조용해진 뒤 약 70초. 보내고 ACK를 못 받은 바이트가 있으면 `TCP_USER_TIMEOUT` 약 70초) 뒤 닫으므로(`transport/server.md` "반쯤 열린 연결"), 그 기한만큼 없음을 세기 시작하는 때가 늦어진다.
- **잠깐의 망 끊김도 없음으로 센다.** TCP keepalive 때문에 망이 끊긴 채 탐침 넷이 모두 답을 못 받으면 살아 있는 실행기의 연결도 닫혀(`closed`·`withdrawn`) 이 박자가 없음을 세기 시작한다. 약 40초는 첫 무응답 탐침부터 만료 검사까지이고 견디는 단절의 고정 길이가 아니다: 31초 단절로도 끊길 수 있고 45초 단절에도 살 수 있다(탐침 시점과 새 수신에 달렸다). 실행기가 다시 붙어 판정 시간 안에 다시 인정되면 옮기지 않고, 그 안에 다시 인정되지 못하면 살아 있는 실행도 `unknown_running`으로 옮긴다(`transport/server.md` "반쯤 열린 연결").
- **단조 시계 포트가 진짜 단조 시계여야 한다.** 포트에 벽시계를 넘기면 벽시계의 보정이 끊긴 시간으로 세어진다. 이 박자는 앞으로 뛴 것을 알아채지 못하고, 뒤로 간 것도 `absentSince`보다 이를 때만 `clock_regressed`로 안다(직전 박자의 값보다만 이른 후퇴는 알아채지 못한다).
- **장부가 실패 상태이면 새 복원기가 1단계를 마칠 때까지 옮기지 않는다.** 1단계 뒤에는 복원이 끝나지 않았어도 옮길 수 있다. 위 "장부 쓰기와 실패".
- **표 조회 안에서만 세대 읽기가 실패하는 복원기는 구별하지 못한다.** 한 박자 안에서 세대 읽기의 실패가 유지되지 않으면 살아 있는 연결이 빈 표로 보인다. 위 "한 박자의 순서" 2.
- **복원기 객체가 다르면 모두 끊긴 것으로 보인다.** 연결 표는 복원기의 객체 동일성으로 이번 복원의 인사를 가른다. 포트의 `restorer`가 연결 표의 `step`에 넘긴 것과 다른 객체면 `occupancy`가 빈 목록이고, 이 박자는 그것을 "모두 없음"과 구별하지 못한다. 세대를 모르는 경우만 `links_unknown`으로 가른다.
- **기억 밖에서 시작해 끊긴 실행기는 놓친다.** 기억은 박자가 본 것만 담는다. 두 박자 사이에 연결·배정·시작·끊김이 모두 일어나면 그 실행기는 `never_seen`이고 감독이 다시 뜰 때까지 옮겨지지 않는다(아래 "뒤 조각이 지킬 것"의 `candidate` 등록이 막는다).
- **세션 실행기는 판정하지 않는다(`not_worker`).** 세션 계약이 연결의 인정을 열 때 함께 정한다.
- **옮긴 실행의 조회 답을 장부에 넘기는 조립이 없다.** 답을 장부에 반영하는 연산은 장부에 있다(`applyExecutorAnswer`: 같은 실행 ID·세대의 "돈다" 답은 상태를 바꾸지 않고 `unknown_running`을 되살리지 않는다). 남은 것은 조회와 대조한 답을 그 연산에 넘기는 조립이다. 그 실행은 종료 확인과 정리의 정상 절차까지 자리를 쥔다(`ledger.md` "남는 한계").

## 이 박자가 하지 않는 것

조회 보내기(옮긴 실행의 조회는 수명 박자가 `unknown_running`에 낸다), 조회 답의 반영, 재전송, 자리 풀기, 연결 닫기, 세션 실행기의 판정, 재시작 뒤의 대조(복원).

## 뒤 조각이 지킬 것

- **끊김 박자를 수명 박자보다 먼저 부른다.** 같은 순환에서 이 박자가 돌아온 뒤에 수명 박자를 부른다. 옮긴 뒤에는 장부가 갱신 기록을 거절하므로, 끊겼다고 판정한 실행기의 실행에 갱신이 적히기 전에 옮겨야 한다(`ledger.md` "판정한 뒤 그 실행기의 실행에 갱신을 기록하기 전에 부른다"). 수명 박자의 연결 포트(`LinkGate.mayIssue`)는 같은 연결을 보고 판정 시간 안에도 끊긴 실행기에는 갱신을 내지 않아야 한다.
- **`watch`를 넘긴다.** `ran`이면 `halted`여도 결과의 `watch`를 다음 박자에 그대로 넘긴다. `not_run`이면 앞 기억을 그대로 쥔다. 넘기지 않으면 위 "기억을 넘기지 않은 결과"대로 끊긴 실행기를 옮기지 못한다.
- **`monotonic`은 한 프로세스 안에서 뒤로 가지 않는 시계다.** 벽시계(`clock`)를 넘기지 않는다. 박자마다 같은 시계를 넘긴다.
- **감독이 다시 뜨면 기억을 비운다.** 단조 시각의 기점이 프로세스마다 달라 옛 기억의 시각으로 잰 경과는 뜻이 없다. 저장했다가 다시 넘기지 않는다.
- **연결 표가 `candidate`를 낼 때 기억에 `{ executorId: 주체 이름, absentSince: null }`을 더한다.** 박자 사이에 붙어 배정·시작된 뒤 끊긴 실행기를 놓치지 않고, 박자 사이의 재인정을 옛 없음 시각으로 세지 않는다. 연결을 본 기록이라 판정을 이르게 하지 않는다. 기억의 `absentSince`를 지어 넣거나 앞당기지 않는다(연결이 실제로 사라진 순간보다 이른 값은 판정을 이르게 한다).
- **`restorer`는 연결 표의 `step`·`check`에 넘기는 그 객체다.** 다시 복원하면 둘을 함께 바꾼다. 그 객체에서 **한 박자 안의 세대 읽기 실패는 유지돼야 한다**(한 번 `null`이거나 던진 뒤 같은 박자 안에서 다시 값을 내지 않는다). 이 조건이 깨지면 살아 있는 연결이 빈 표로 보여 판정 시간 뒤 살아 있는 실행을 옮길 수 있다.
- **반쯤 열린 연결을 닫는다.** 소켓 조립은 상대가 사라진 연결을 알아채 `closed` 사건으로 연결 표에 알린다. 지금은 TCP keepalive가 운영체제 기한 뒤 닫는다(`transport/server.md` "반쯤 열린 연결", 값은 T1 실측 뒤 조정). 이 박자는 연결 표가 인정하는 동안 옮기지 않는다.
- **판정 시간은 정책으로 넘긴다.** 계약의 `DISCONNECT_JUDGE_MS`(기본값, 관리자 미확정)이거나 시험 클러스터에서 잰 값이고 `RUN_LEASE_MAX_MS` 이상이다.
- **포트는 읽기 실패를 빈 목록으로 바꾸지 않는다.** 연결 표·실행 목록을 읽지 못하면 던지거나 모름을 낸다. 빈 성공 목록은 "아무도 없다"로 읽힌다.
- **실패한 장부는 다시 열어 복원하고, 복원이 실패하면 그 단계부터 다시 한다.** 이 박자가 `links_unknown`으로 쓰지 않는 것은 새 복원기가 1단계를 마치기 전까지다. **1단계 뒤에는 복원이 끝나지 않았어도 박자가 돌고 옮길 수 있으므로, 복원이 끝나기 전의 박자를 막으려면 조립이 복원이 끝날 때까지 이 박자를 부르지 않는다.**
- **옮긴 실행은 다시 붙은 뒤 같은 실행 ID로 조회만 한다.** 새 실행 ID로 다시 보내지 않는다. 취소·기한이 걸린 실행은 종료가 먼저다(수명 판단이 그렇게 낸다). 조회의 답은 대조한 뒤 `applyExecutorAnswer`에 넘긴다. 답이 `not_known`이어도 종료의 증거로 쓰지 않는다.
- **`ledger_failed`면 기억이 남아 장부가 건강한 동안 다음 박자가 다시 부른다. `threw`·`malformed_answer`나 `halted`면 장부를 다시 읽어 그 실행기의 실행이 `unknown_running`인지 본다.**
