# 답을 받지 못한 지시의 재전송 (`resend.ts`)

배정기 순환의 한 박자다. 장부의 `unansweredInstructions()`가 낸 지시(시작, 취소, 확정)마다 그 항목의 값만으로 초안을 다시 만들어 봉하고 지정 실행기의 연결에 싣는다. **장부에 쓰는 것은 시작의 송신 표식(`markStartDispatch`) 하나뿐이다**: 지시 줄·실행 줄은 쓰지 않고, 표식도 공유 함수 `sendInstruction`(`send-gate.md`)이 싣기 직전에 적는다. 새 요청 ID를 만들지 않는다. 실행기는 같은 요청 ID·같은 본문의 재전송에 이미 낸 영수증을 다시 보내므로(`src/ledger/ledger.md` "답을 받지 못한 지시"), 답이 오면 그 지시는 읽기에서 사라지고 재전송은 저절로 멈춘다.

장부·접수·연결·시계·난수·서명·내보내기는 포트로, 정책과 앞 박자들의 기억(지시마다 마지막으로 내보낸 시각)은 인자로 받는다. 소켓·타이머·시계·난수를 직접 부르지 않는다(시험이 소스를 읽어 지킨다). 쥐는 것은 같은 장부 포트로 박자가 진행 중이라는 표시 하나다.

## 공개 면

```ts
resendTick(ports: ResendPorts, policy: ResendPolicy, input: ResendTickInput): Promise<ResendTickResult>

ResendPorts = {
  ledger: Pick<Ledger, "unansweredInstructions" | "markStartDispatch">  // 표식은 그 항목을 다시 읽은 이 객체로 적는다
  intake: Pick<Restorer, "intakeOpen">        // 시작을 다시 낼 때만 본다
  links: ResendLinkGate                        // { mayIssue(executorId, "task_start" | "task_cancel" | "result_finalize"): { ok: true } | { ok: false, reason } }, 동기
  clock: Clock                                 // 장부 시계와 같은 시계
  random: Random                               // nonce만
  signer: Signer
  sink: InstructionSink
  beatValid?: () => boolean                    // 박자 유효 문. 공유 함수가 표식·송신 바로 앞에서 본다. 빠지면 늘 유효(조립은 반드시 넘긴다)
}
ResendPolicy = { resendEveryMs: number }       // 양의 안전 정수
ResendTickInput = { lastResends: { requestId: string, at: number }[] }

ResendTickResult =
  | { kind: "not_run", reason: "clock_unavailable" | "policy_rejected" | "input_malformed" | "read_unknown" | "stop_generation_unknown" | "tick_in_progress" }
  | { kind: "ran", instructions: ResendOutcome[], halted: "threw" | null, haltedAt: string | null }

START_LAST_SEAL_MS = 19000   // 시작을 다시 봉할 수 있는 발행 뒤 거리
```

`ResendLinkGate`는 계약 v1의 `mayIssue(action, link, now)`를 그 실행기의 연결과 부르는 순간의 시각으로 부른 답이다(수명 박자의 `LinkGate`와 같은 뜻, 동작 이름만 넓다).

| 지시마다 (`ResendOutcome`) | 뜻 |
|---|---|
| `resent` + `executorId`, `sealedAt`, `at` | 같은 요청을 새 봉투에 담아 실었다(`sent`는 받았다는 뜻이 아니다). `sealedAt`은 봉할 때 읽은 시각, `at`은 다음 박자의 `lastResends`에 넘길 시각(내보내기 포트가 돌아온 뒤 읽은 시각, 읽지 못하면 그 봉투의 시한) |
| `held` + `lastAt` | `lastAt`(항목의 발행 시각과 넘겨받은 마지막 송신 시각 가운데 늦은 것)부터 간격이 지나지 않았다 |
| `answered` | 싣기 직전에 다시 읽으니 더는 답을 기다리는 지시가 아니다 |
| `not_rebuildable` | 장부가 본문을 다시 만들 수 없다(`rebuild: null`). 부르는 쪽은 같은 실행 ID를 조회한다 |
| `start_expired` + `issuedAt`, `expiresAt` | 시작의 재전송 한도(발행 + 19000ms)가 지났다. `expiresAt`은 그 시작의 모든 봉투가 갖는 시한(발행 + 30000ms) |
| `stop_generation_mismatch` + `stopGeneration`, `currentStopGeneration` | 항목의 정지 세대가 장부의 지금 세대와 다르다 |
| `withheld` + `reason` | 내보내기 포트를 부르지 않았다. 대부분 봉하기 전이고, 시작의 마지막 시계 읽기(아래 순서 12·14)에서 난 `clock_unavailable`은 이미 서명한 봉투를 버린 것이다(12에서 시계 함수를 얻지 못했으면 이번 시도의 표식 호출 0이고(같은 열기의 앞선 시도가 적은 행은 남을 수 있다), 14의 읽기가 던지거나 무효면 송신 표식은 남는다): `session_run`(세션 실행의 지시), `run_unknown`(장부가 모른다고 옮긴 `unknown_running` 실행의 시작), `stop_recorded`(종료가 적힌 실행의 시작), `intake_closed`(시작만), `no_connection`(연결 포트가 문자열 `reason`과 함께 거절), `link_unknown`(연결 포트가 던지거나 답이 정의 밖), `clock_unavailable`(시계가 던지거나, 양의 안전 정수가 아니거나, 앞서 읽은 시각보다 이름), `read_unknown`(싣기 직전의 다시 읽기가 모름이거나 같은 요청 ID의 칸이 처음과 다름. 대조하는 칸은 동작·실행 ID·실행 세대·지정 실행기·정지 세대·발행 시각과 본문을 다시 만들 칸 전부), `check_malformed`(시작의 마지막 확인 답이 `null`도 이 박자의 거절도 아님. 공유 함수가 싣지 않는다. 이 박자의 확인은 늘 둘 중 하나를 내므로 계약 밖 입력의 결과다), `beat_closed`(공유 함수 안에서 본 박자 유효 문이 닫힘. 서명한 봉투를 버린다. 시작이면 표식 앞의 문(13)에서 닫히면 **이번 시도의 표식 호출 0**이고, 표식 뒤 마지막 판정의 문(14)에서 닫히면 **이번 시도의 표식 호출 1회·송신 0**이다. 그 호출이 새로 쓴 행은 `created: true`면 1, 같은 열기의 앞선 시도(예: 연결이 없어 싣지 못한 첫 송신)가 이미 적어 `created: false`면 0이고 이미 있는 행이 1이다. 어느 쪽이든 같은 열기의 앞선 시도가 적은 표식 행은 그대로 남을 수 있다: 표식은 열기마다 처음 한 번만 적는다. 취소·확정은 15 앞의 문에서 닫히며 표식과 무관하다) |
| `not_sealed` + `reason`(`field`, `sealReason`) | 초안·봉하기의 거절 이름, `draft_threw`, `seal_threw`. 실리지 않았다 |
| `not_sent` + `reason`, `delivery`, `executorId`, `sealedAt` (+ `at`, `markReason`) | `no_connection`·`too_late_to_send`(포트가 싣지 않았다고 답함), `sink_unavailable`(`sink`나 `sink.send`를 얻다 던지거나 함수가 아니어서 포트를 부르지 않음. 이번 시도는 새 표식을 쓰지 않았다. 앞선 시도의 표식은 남아 있을 수 있다), `start_unmarked`(시작의 송신 표식이 `ok`가 아니어서 포트를 부르지 않음. `markReason`에 장부의 거절 이름·`threw`·`malformed_answer`·`envelope_unreadable`. 실제 장부를 표식 포트로 쓰면 이번 시도의 표식은 없지만, 주입한 표식 포트가 커밋한 뒤 던지면 표식 한 줄이 남는다: `send-gate.md` "표식 뒤에 싣지 않고 돌아가는 길"). 이 넷은 `delivery: "not_sent"`, `at` 없음. `send_threw`·`send_answer_malformed`(`delivery: "unknown"`: 실렸을 수 있다. `at`은 `resent`와 같은 규칙) |
| `malformed` + `field` | 항목의 칸을 읽을 수 없다(`requestId`를 읽지 못했으면 `null`). 같은 요청 ID의 항목이 둘 이상이면 모두 `malformed`(`requestId`) |

모든 항목(`malformed` 밖)은 `requestId`, `runId`, `action`을 싣는다. 결과에는 본문·자격 참조·봉투·서명·nonce가 없다(시험이 결과의 JSON에 자격 digest·서명·nonce가 없음을 본다).

## 한 박자의 순서

1. **박자 전체의 전제.** 장부 포트(`ports.ledger`를 한 번 읽어 얻은 객체. 읽기 메서드를 붙인 함수도 받는다. 읽다 던지거나 객체도 함수도 아니면 `read_unknown`), 같은 장부 포트로 진행 중인 박자가 없음(있으면 `tick_in_progress`, 읽기 0), 시계, 정책의 간격, `lastResends`의 꼴, `unansweredInstructions()`. 읽기의 `known`이 불리언 `true`가 아니거나 값의 꼴이 틀리거나 던지면 `read_unknown`이고 아무것도 봉하지 않는다. 정지 세대가 `null`(정지 기록 없음)이면 `stop_generation_unknown`이다. 정지 기록이 없으면 장부가 지시를 적지 않으므로 대조할 세대를 모르는 읽기다.
2. **항목마다, 읽기의 순서대로** 아래를 차례로 본다. 앞에서 걸리면 그 이유가 결과다.

| 차례 | 보는 것 | 걸리면 |
|---|---|---|
| 1 | 다시 읽기: 장부를 다시 읽어 같은 요청 ID의 항목을 찾는다. 판단은 모두 이 읽기의 값으로 한다 | `withheld`(`read_unknown`), `answered`, `malformed` |
| 2 | 세션의 시작·정지 | `withheld`(`session_run`) |
| 3 | 본문 칸 | `not_rebuildable` |
| 4 | 시계(박자 처음과 앞 항목의 시각보다 이르지 않음) | `withheld`(`clock_unavailable`) |
| 5 | 시작: 시각이 발행 + 19000ms 이하 | `start_expired` |
| 6 | 항목의 정지 세대 = 다시 읽은 장부의 정지 세대 | `stop_generation_mismatch` |
| 7 | 시작: 실행 상태가 `unknown_running`이 아님, 같은 실행에 종료가 적히지 않음(같은 읽기에 그 실행의 종료 항목이 없고 상태가 `stopping`이 아님), 접수가 열림 | `withheld`(`run_unknown`, `stop_recorded`, `intake_closed`) |
| 8 | 간격: `시각 − max(항목의 발행 시각, lastResends의 그 요청 ID) >= resendEveryMs` | `held` |
| 9 | 연결: `links.mayIssue(지정 실행기, 동작)` | `withheld`(`no_connection`, `link_unknown`) |
| 10 | 시작: 시계를 다시 읽어 발행 + 19000ms 이하 | `withheld`(`clock_unavailable`), `start_expired` |
| 11 | 초안(항목의 값만) → `sealDraft(초안, 봉하는 시각)` | `not_sealed`, 시작의 `too_late_to_send`는 `start_expired` |
| 12 | 시작이면 14의 시계 읽기에 쓸 시계 함수(`ports.clock`의 `now`)를 먼저 얻어 둔다(얻지 못하면 표식 없이 끝). 그다음 공유 함수가 진입 때 입력의 칸을 한 번씩 읽어 쥔다: 내보내기 포트의 수신 객체(`ports.sink`)와 함수(`sink.send`), 박자 유효 문(`ports.beatValid`), 시작이면 표식 입력의 칸(표식 포트와 그 메서드, 시각, 마지막 확인). 그 뒤에는 쥔 값만 쓴다(`send-gate.md` "차례" 2). 포트를 얻지 못했으면 시작은 시계를 다시 읽어 발행 + 19000ms 이하인지 먼저 보고(표식 없이), 그다음 포트를 부르지 않는다 | `withheld`(`clock_unavailable`), `start_expired`, 그다음 `not_sent`(`sink_unavailable`) |
| 13 | 시작이면 박자 유효 문 → 송신 표식: 1에서 다시 읽은 그 장부 객체로 `markStartDispatch({ runId, requestId, now: 마지막으로 읽은 시각 })`. 유효 문이 닫혔으면 표식 없이 끝. `ok`가 아니면 포트를 부르지 않는다 | `withheld`(`beat_closed`, 이번 시도의 표식 호출 0. 앞선 시도의 행은 남을 수 있다), `not_sent`(`start_unmarked`) |
| 14 | 시작이면 표식 뒤 마지막 판정: 박자 유효 문 → 12에서 얻은 시계 함수로 다시 읽어 발행 + 19000ms 이하(봉한 봉투는 버린다. 표식은 남는다) | `withheld`(`beat_closed`, 이번 시도의 표식 호출 1회·송신 0. 새 행은 `created`에 따라 1 또는 0), `withheld`(`clock_unavailable`), `start_expired` |
| 15 | 시작이 아니면 박자 유효 문을 본 뒤, 12에서 쥔 함수를 수신 객체를 `this`로 해 부른다. 공유 함수는 포트의 답을 받는 즉시 돌아온다 | `withheld`(`beat_closed`, 취소·확정의 문이 닫힘. 표식과 무관), `not_sent`(`no_connection`, `too_late_to_send`) |
| 16 | 박자: 포트의 답이 `sent`이거나 실렸는지 모르는 결과(포트가 던짐, 정의 밖의 답)일 때만 시계를 읽어 `at`을 정한다(읽지 못하면 봉투의 시한). 12~15에서 돌아온 다른 결과에는 읽지 않는다 | `resent`, `not_sent`(`send_threw`, `send_answer_malformed`) |

12~15는 공유 함수 `sendInstruction` 안에서 이 차례로 하고(`send-gate.md`), 16은 공유 함수가 돌아온 뒤 재전송 박자가 한다. 포트 직전의 시계 읽기(12·14)는 공유 함수 안에서 부르는 박자의 확인이고, 송신 뒤의 읽기(16)는 다음 박자에 넘길 `at`을 위한 것이다. 4의 시계 읽기부터 15의 포트 호출까지 `await`가 없다. 봉하는 시각은 취소·확정이면 4에서, 시작이면 10에서 읽은 값이다. **표식의 커밋은 시작의 마지막 시계 읽기(14)보다 앞이다**: 커밋(fsync)에 걸린 시간을 그 읽기가 잰다. 마지막 시계 읽기와 포트 호출 사이에는 포트의 접근자도 다른 포트 호출도 없고, 표식과 포트 호출 사이에는 박자 유효 문과 그 시계 읽기뿐이다. 유효 문을 시계 읽기 앞에 두는 것은 유효 문 안의 읽기(조립에서는 장부 건강·허가)에 쓴 시간까지 시작 한도가 보게 하려는 것이다: 반대 차례면 발행 + 19000ms에 확인한 시작이 그 읽기 1ms 뒤인 19001ms에 포트에 들어간다. 남는 틈은 시계 함수의 호출 자체다(박자 기한과 시작 한도의 시계가 달라 한 번에 볼 수 없다. `send-gate.md` "남는 틈"). 취소·확정은 13·14 없이 12·15만 한다(표식을 부르지 않는다). 취소·확정도 같은 순서로 포트를 얻고 부른다(한도는 시작에만 걸린다). 시계를 다시 읽을 때마다 그 박자에서 앞서 읽은 시각보다 이르면 읽지 못한 것이다.

## 같은 요청

- **초안은 항목의 값만으로 만든다.** 실행 줄을 따로 읽지 않는다. 시작은 `startDraft({ run: { runId, runGeneration, executorId, kind: "worker", ...rebuild }, requestId, stopGeneration, issuedAt })`, 취소는 `stopDraft`, 확정은 `finalizeDraft`이고 요청 ID·정지 세대는 항목의 값이다. 그래서 받는 쪽·요청 ID·본문·본문 digest·머리의 두 세대가 처음 봉투와 같다.
- **새로 만드는 것.** 모든 동작에서 nonce·서명은 새것이다. 머리의 시각은 봉투 모듈의 시각 규칙을 따른다(`envelopes.md`): 시작은 장부의 발행 시각을 그대로 실어 `issued_at`·`expires_at`이 처음과 같고, 취소·확정은 두 시각도 봉하는 때의 것으로 바뀐다. 실행기는 취소·확정의 재전송을 요청 ID와 본문 digest로 대조하므로 새 시각의 봉투도 같은 요청이다.
- **본문 칸은 읽은 값을 칸마다 한 번 옮겨 적는다.** 칸의 종류(문자열, 시각, 정수)가 틀리면 그 항목은 `malformed`(`rebuild`)이고, 값이 계약 밖이면 초안·봉하기(계약의 `sealEnvelope`)가 거절한다. 비어 있는 칸을 채우지 않는다.
- **싣기 직전의 다시 읽기는 본문 칸도 대조한다.** 다시 읽은 항목의 머리 칸이나 본문을 다시 만들 칸이 처음 읽은 것과 하나라도 다르면 `read_unknown`으로 내지 않는다. 장부의 지시 줄은 적은 뒤 바뀌지 않으므로 다르면 틀린 읽기이고, 그대로 봉하면 같은 요청 ID에 다른 본문 digest가 실린다.

## 시작

- **한도.** 시작은 발행 + `START_LAST_SEAL_MS`(봉투 모듈의 규칙: 시한 30000 − (`DELIVERY_MAX_MS` + `CLOCK_SKEW_MS`) = 19000ms) 뒤에 봉하지 않고 `start_expired`를 낸다. 봉투 모듈이 그보다 일찍 `too_late_to_send`를 내도 `start_expired`다. 그래서 두 규칙이 어긋나도 늦은 시작이 나가지 않는다. 새 시각으로 되살리지 않는다.
- **판단한 뒤에 흐른 시간.** 연결·서명 포트 안에서도 시각이 흐르므로, 시작은 연결 확인 뒤에 시계를 다시 읽어 그 시각으로 봉하고, 봉한 뒤 내보내기 포트의 수신 객체와 함수를 얻고 송신 표식을 커밋한 다음 부르기 직전에 한 번 더 읽는다. 어느 쪽이든 한도를 넘었으면 원래 두 시각을 실은 `start_expired`이고 내보내기 포트를 부르지 않는다. 시계를 읽지 못하면 `withheld`(`clock_unavailable`)이고 역시 부르지 않는다.
- **이 박자가 지키는 범위.** 마지막 시계 읽기가 보는 것은 **발행 + 19000ms 한도 하나**다. 시작의 작업 기한에 남아야 하는 여유(`DELIVERY_MAX_MS` + `CLOCK_SKEW_MS` = 11000ms)는 봉할 때(`sealDraft`)와 실제로 싣는 순간의 내보내기 포트가 본다. 그래서 봉한 뒤 서명 포트 안에서 작업 기한의 여유가 모자라게 되면 이 박자는 포트를 부르고, 포트가 `too_late_to_send`로 거절한다. 그 읽기와 실제로 싣는 순간 사이에도 시각은 흐르므로, 싣는 순간의 한도도 내보내기 포트가 지킨다(`ports.ts` `InstructionSink`의 조건). 마지막 읽기에서 작업 기한을 다시 보지 않는 것은 그 규칙을 가진 함수가 `sealDraft` 하나뿐이고, 다시 부르면 난수·서명 포트를 다시 부르기 때문이다.
- **송신 표식(D-90의 전제).** 시작은 그 장부 열기의 표식이 `ok`로 커밋된 뒤에만 싣는다. 감독이 다시 떠 장부를 다시 연 뒤의 재전송은 새 열기의 표식을 남기므로, 그 뒤 다시 연 장부의 자동 닫기는 그 실행을 닫지 않는다(`sent_by_other_open`). 표식이 거절되면(못 씀, 정지·접수 닫힘 등) 싣지 않고 `start_unmarked`이며 다음 박자가 다시 시도한다. 마지막 시계 읽기가 막으면 표식만 남고 실리지 않는다(자동 닫기를 덜 하는 쪽, `send-gate.md` "표식 뒤에 싣지 않고 돌아가는 길").
- **D-90의 조건 (2)의 재료.** 이 박자는 발행 + 19000ms 뒤에 그 시작을 봉하지 않고, 그 시작의 봉투는 다시 봉해도 시한이 모두 발행 + 30000ms다. 그래서 장부의 발행 시각만으로 "더 보내지 않고 마지막 봉투의 시한이 지남"의 시각을 정할 수 있다. `run_unknown`은 그 한도 안의 봉투를 더 줄일 뿐이라 이 시각을 늦추지 않고, 표식도 쓰지 않아 다른 열기의 표식(`sent_by_other_open`)을 새로 만들지 않는다. 다시 읽은 시작의 본문을 다시 만들 수 있고(3) 유효한 시각으로 5의 시한 판정에 닿으면, 한도가 지난 뒤의 결과는 상태와 무관하게 `start_expired`다. 본문을 다시 만들 수 없는 옛 판의 시작(이관 전에 쓴 시작, `rebuild: null`)은 시각과 무관하게 3에서 `not_rebuildable`로 끝나 같은 실행 ID를 조회하고, 장부의 D-90 자동 닫기도 그 실행을 닫지 않는다(`started_before_migration`). 단 배정·시작 박자와 다른 경로가 같은 시작을 더 봉하지 않는다는 것은 각 경로의 조건이다(배정·시작 박자는 `startRun` 직후 한 번만 봉한다). 자리를 푸는 판단(D-90)은 이 PR에 없다.
- **모른다고 옮긴 실행의 시작은 다시 내지 않는다**(`run_unknown`). 끊김 박자(`markLostFor`)나 복원 3단계(`markLost`)가 `unknown_running`으로 옮긴 실행은 되살리지 않고, 다시 붙은 뒤 같은 실행 ID로 조회만 한다(D-92, `link-loss.md` "옮긴 실행은 다시 붙은 뒤 같은 실행 ID로 조회만 한다"). 처음 봉투를 받지 못한 실행기가 새 연결로 그 시작을 받으면 감독이 갱신하지 않을 실행을 연다. 조회는 수명 박자의 일이다. 이 판정은 5의 시한 판정 뒤라, 시한 판정에 닿은 시작은 발행 + 19000ms가 지났으면 상태와 무관하게 `start_expired`다. 본문을 다시 만들 수 없는 옛 시작은 그 전 3에서 `not_rebuildable`이다(위 "D-90의 조건 (2)의 재료"). 종료·확정은 상태가 `unknown_running`이어도 그대로 다시 낸다(멈춰야 할 실행을 멈춘다). 주로 걸리는 길은 감독이 다시 뜬 뒤다: 복원 3단계는 판정 시간을 기다리지 않고 옮기므로 발행 + 19000ms 안의 시작이 남아 있을 수 있다. 운영 중 끊김은 없음이 판정 시간(`RUN_LEASE_MAX_MS` 이상)을 넘어야 옮기므로 보통 그 안에 들지 않는다.
- **종료가 적힌 실행의 시작은 다시 내지 않는다**(`stop_recorded`). 장부는 "같은 실행에 시작과 종료가 함께 답이 없으면 어느 쪽을 보낼지는 부르는 쪽이 정한다"고 남겼다(`ledger.md` "시작은 시한 안에서만 다시 보낸다"). 실행기가 시작을 받은 적이 없다면 시작을 다시 보내면 열자마자 닫힐 작업자를 띄우고, 받았다면 시작의 재전송은 영수증을 다시 받는 것뿐이다. 종료는 따로 다시 낸다. 모르는 실행의 종료에 실행기는 답하지 않으므로, 실행기가 시작을 받은 적이 없으면 그 종료는 답 없이 간격마다 다시 나간다(아래 "남는 한계").
- **박자가 무효면 표식을 적지 않고 싣지 않는다**(`withheld`·`beat_closed`). 송신 표식은 이 박자의 유일한 장부 쓰기다. 선택 포트 `beatValid`는 이 박자가 아니라 공유 함수(`sendInstruction`)가 본다: 내보내기 포트의 수신 객체와 `send`를 얻은 뒤 시작의 표식 바로 앞, 그리고 모든 송신(시작·취소·확정) 바로 앞이다(`send-gate.md` "차례"). 이 박자가 공유 함수를 부르기 전에 보면 그 접근자 안에서 흐른 시간을 보지 못한다. `true`가 아니거나 던지면 그 뒤를 하지 않는다. 시작의 표식 뒤 마지막 판정(시계 확인 앞)에서 닫히면 이번 시도가 쓴 표식만 남는다(`withheld`·`beat_closed`, 표식 1행·송신 0). 표식 앞에서 닫히면 이번 시도는 표식을 쓰지 않지만, 같은 열기의 앞선 시도가 적은 행은 남아 있을 수 있다. 포트가 빠지면 늘 유효다(이 부품 단독의 쓰임).
- **접수가 닫히면 시작을 다시 내지 않는다**(`intake_closed`). 시작은 새 일을 연다. 정지(세대가 오름)는 6의 대조가 막고, 복원 중·사본 보류 같은 다른 닫힘은 이 확인이 막는다. 종료·확정은 접수와 무관하게 다시 낸다(장부도 정지 중에 종료를 적는다).

## 정지 세대

항목의 `stopGeneration`(그 지시를 적을 때의 세대)이 다시 읽은 장부의 `stopGeneration`과 다르면 봉하지 않는다. 실행기가 새 세대를 적용한 뒤에는 옛 세대의 지시를 받지 않고, 적용하기 전이면 장부가 이미 넘어선 세대의 지시가 실행된다(`ledger.md` "항목의 정지 세대가 장부의 지금 세대와 다르면 보내지 않는다"). 세대를 맞춘 뒤 종료는 새 세대의 비상 종료로, 확정은 새 세대·새 요청 ID의 확정으로 다른 조각이 낸다.

## 두드리지 않기

- **간격의 기준은 `max(항목의 발행 시각, lastResends의 그 요청 ID)`다.** 장부는 송신마다 시각을 적지 않으므로(송신 표식은 열기마다 처음 한 번만 적는다) 마지막 송신 시각은 부르는 쪽의 메모리다. 발행 시각도 기준에 넣어, 다른 박자(배정·시작, 수명)가 방금 적고 실은 지시를 곧바로 다시 내지 않는다. 감독이 다시 뜨면 `lastResends`는 비고, 발행 뒤 간격이 지난 지시는 첫 박자에 바로 나간다.
- **부르는 쪽이 넘기는 것:** 결과의 `resent`와 `delivery: "unknown"`인 `not_sent`의 `{ requestId, at }`(`sealedAt`이 아니다). `at`은 내보내기 포트가 돌아온 뒤 읽은 시각이라 실은 시각보다 이르지 않다. 그래서 포트 안에서 시간이 걸려도(봉한 뒤 5000ms 뒤에 실림) 다음 박자는 실은 때부터 간격을 잰다. 그 시계를 읽지 못하면(던짐, 뒤로 감) 봉투의 시한을 쓴다. 포트는 시한 뒤에 싣지 않으므로 실은 시각의 상한이고, 그만큼 다음 재전송이 늦어질 뿐 앞당겨지지 않는다.
- **전달이 모름(`send_threw`·`send_answer_malformed`)일 때의 간격은 내보내기 포트의 조건에 기댄다.** 이때도 `at`은 포트가 돌아온 뒤 읽은 시각이다. 그 값이 실은 시각의 상한인 것은 **전달을 확정할 수 없는 모든 끝(예외, 정의 밖의 반환값)에서 내보내기 포트가 맡은 쓰기를 이미 끝냈거나 거둔 경우**다. 그렇게 끝난 뒤에도 맡은 쓰기가 이어지는 포트에서는 그 쓰기가 `at` 뒤에 실릴 수 있고, 같은 요청이 간격보다 짧게(예: 1ms) 두 번 실릴 수 있다. 같은 요청이라 실행기는 앞 영수증으로 답한다. 이 조건은 내보내기 포트를 조립할 때 지킨다(아래 "뒤 조각이 지킬 것").
- **멈춤.** 실행기가 답하면 그 지시는 읽기에서 사라진다(`answered`, 또는 다음 박자에 항목이 없다). 앞 항목을 내보내는 동안 온 답은 1의 다시 읽기가 받아 낸다.
- **시작과 간격.** 간격이 19000ms보다 크면 시작은 한 번도 다시 나가지 않는다(간격을 발행 시각부터 세므로). 정책 검증은 양의 안전 정수만 본다.
- **취소를 다시 낸 직후의 조회.** 수명 판단은 `stopping` 실행의 응답 대기를 장부의 발행 시각(`instructionTimes`의 `lastStopAt`)부터 센다. 재전송은 장부에 새 시각을 적지 않으므로, 처음 발행부터 `answerTimeoutMs`가 지난 취소를 다시 내면 그 직후의 수명 박자는 응답 대기가 이미 끝난 것으로 보고 같은 실행을 조회할 수 있다. 조회는 상태만 묻고 실행을 바꾸지 않는다.
- **확정을 다시 낸 뒤에는 지금의 수명 판단이 그 실행을 조회하지 않는다.** 결과 쪽 상태는 수명 판단의 확정·대기 분기로만 가고, 수명 박자는 `resultSettled`를 거짓으로 넘긴다. 그래서 `answerTimeoutMs` 20000에서 확정을 적고 30000ms 뒤에 다시 낸 `ready_result`는 `wait`, 23000ms 뒤에 다시 낸 `failed_stopped`는 `finalize_withheld`이고 조회는 0건이다. 확정에 답이 없는 실행을 조회하는 일은 뒤 조각의 몫이다.

## 수명 박자와 겹치지 않는가 (같은 실행의 종료 지시)

- **이 박자는 종료 지시를 만들지 않는다.** 장부 포트의 쓰기는 시작의 송신 표식뿐이고, 다시 내는 지시는 읽기의 요청 ID 그대로다.
- **수명 박자는 종료가 적힌 실행에 새 종료를 적지 않는다.** 판단이 종료를 내도 그 실행의 `lastStopAt`이 있으면 조회로 가고(`cause: "stop_already_recorded"`), 쓰기 직전에 다시 읽어 새로 보이면 `superseded`다(`life-loop.md` "이미 적힌 종료"). 그래서 수명 박자의 경로만 보면 실행 하나에 종료 지시는 하나이고, 이 박자는 그 하나를 같은 요청 ID로 다시 낸다.
- **다른 경로는 둘째 종료를 적을 수 있다.** 본체의 이은 부탁 취소(`cancelToolRequest`)는 `stopping` 실행에도 호출 ID를 요청 ID로 한 `task_cancel`을 적는다(`ledger.md` "이은 부탁의 취소"). 그러면 읽기에 같은 실행의 종료가 둘 나오고, 이 박자는 각각을 자기 요청 ID·본문으로 다시 낸다. 실행기는 지금 세대의 새 요청 ID 취소에 새 접수 영수증을 내므로 둘 다 답을 받을 수 있다. 이 박자가 셋째 지시를 만드는 일은 없다.
- **겹쳐 부르기.** 이 박자와 수명 박자가 같은 장부에 겹쳐 돌아도 이 박자는 송신 표식(`start_dispatches`) 밖을 쓰지 않으므로 수명 박자의 다시 읽기를 흔들지 않는다. 수명 박자가 방금 적은 종료는 발행 시각 기준의 간격에 걸려 곧바로 다시 나가지 않는다.

## 박자가 멈출 때

- **한 항목의 실패는 그 항목의 결과다.** 다시 읽기·시계·접수·연결·초안·서명·난수·내보내기의 예외와 거절은 위 표의 이름으로 그 항목에 남고, 박자는 다음 항목을 본다. 포트 묶음에서 `random`·`signer`를 얻다 던지면 `not_sealed`(`seal_threw`), `sink`나 `sink.send`를 얻다 던지면 `not_sent`(`sink_unavailable`)이고 `halted`가 아니다. 다만 결과는 어느 단계에서 던졌는지에 따라 다르다. `clock`을 얻다 던지면 내보내기 포트를 부르기 전에는 `withheld`(`clock_unavailable`)이지만, 포트가 돌아온 뒤에는 결과가 포트의 답대로(실었으면 `resent`)이고 `at`은 그 봉투의 시한이다(부르는 쪽은 그 `at`을 기억한다). 시작에서 `sink`나 `sink.send`를 얻다 던지면 그 뒤의 마지막 시계 읽기가 먼저다(순서 12의 차례. 송신 표식은 적지 않는다): 한도를 넘었으면 `start_expired`, 그 시계까지 던지면 `withheld`(`clock_unavailable`)이고, 둘 다 아닐 때만 `not_sent`(`sink_unavailable`)다. 표식 포트(`ledger.markStartDispatch`)를 부르다 던지면 `not_sent`(`start_unmarked`, `markReason: "threw"`)다.
- **그래도 항목 처리 밖으로 예외가 나오면** 남은 항목을 하지 않고 `halted: "threw"`, `haltedAt`은 그 항목의 요청 ID다. 그때까지의 결과는 그대로 싣는다(시험이 본다). 내보내기를 부른 뒤였으면 그 항목을 `not_sent`(`send_threw`, `delivery: "unknown"`, `at`은 그 봉투의 시한)로 싣는다. 포트의 메서드 호출은 모두 예외 처리 안에 있지만, 항목 안에서 포트 묶음의 세 속성(`ports.ledger`·`ports.intake`·`ports.links`)을 읽는 접근은 그 밖에 있다. 이 세 접근(getter)이 던질 때만 이 길로 온다. 장부에는 표식만 쓰고 표식은 항목 처리 안에서 결과가 되므로 멈춰도 잃는 기록은 없다.
- **박자 처음에 장부 포트를 얻지 못하면** 예외를 내지 않고 `not_run`/`read_unknown`이다(아무것도 읽거나 봉하지 않는다).
- **겹쳐 부르기:** 같은 장부 포트 객체로 박자가 진행 중이면 다음 호출은 읽기 없이 `not_run`/`tick_in_progress`다. 다른 포트 객체로 겹쳐 부르면 알아채지 못한다.

## 이 박자가 하지 않는 것

갱신의 재전송(읽기가 내지 않는다. 갱신에는 영수증이 없다), 세션 지시의 재전송(세션 계약 작업이 연다. 세션 실행기가 `session_stop`의 재전송을 같은 요청으로 처리하는지는 확인하지 않았다. `session_start`는 2에서 `session_run`으로 끝나 `run_unknown`에 닿지 않는다. 세션 재전송을 열 때 모른다고 옮긴 실행의 `session_start`도 같은 D-92를 따를지 그 작업이 정한다), 새 요청 ID의 지시, 송신 표식 밖의 장부 쓰기, 조회(`not_rebuildable`·`stop_generation_mismatch` 뒤의 조회는 수명 박자나 부르는 쪽의 일), 받은 적 없는 실행의 자리 풀기(D-90), 본체의 도구 처리기의 취소 포트 어댑터.

## 뒤 조각이 지킬 것

- **`lastResends`를 넘긴다.** `resent`와 `delivery: "unknown"`인 `not_sent`의 `at`을 요청 ID마다 쥐고 넘긴다(`sealedAt`을 넘기면 포트 안의 지연만큼 간격이 짧아진다). 넘기지 않으면 발행 시각부터 간격이 지난 지시를 박자마다 다시 낸다. 읽기에서 사라진 요청 ID는 버려도 된다.
- **박자 사이에도 시계가 뒤로 가지 않게 잇는다**(재기동 포함. `ports.ts`의 비후퇴 시계 전제). 시각을 믿을 수 없으면 시작의 재전송과 D-90의 시간 판정을 보류한다.
- **박자를 직렬화한다.** 앞 박자가 돌아온 뒤에 다음을 부른다(다른 포트 객체로도).
- **서명·시계·연결 확인 포트 안에서 장부의 상태를 바꾸지 않는다.** 다시 읽기 뒤의 동기 포트 안에서 실행을 옮기면 이 박자는 그 쓰기를 보지 못해, 이미 읽은 시작을 그대로 싣는다(아래 "다시 읽기가 막는 범위").
- **`links`를 실제 연결로 잇는다.** 그 실행기의 `Link`와 부르는 순간의 시각으로 계약 v1의 `mayIssue`를 부르고 동기로 답한다.
- **모른다고 옮긴 실행의 조회를 수명 박자에 맡긴다.** 이 박자는 그 실행의 시작을 다시 내지 않고(`run_unknown`) 조회도 하지 않는다.
- **내보내기 포트는 싣는 순간에 정지 세대와 봉투 시한, 시작의 작업 기한 여유를 다시 본다.** 이 박자는 내보내기 포트를 부르기 직전까지 재지만 포트 안의 대기는 재지 못하고, 마지막 시계 읽기는 발행 + 19000ms 한도만 본다(`ports.ts` `InstructionSink`의 조건). 시작의 한도도 마찬가지로 싣는 순간에는 포트가 지킨다.
- **내보내기 포트는 전달을 확정할 수 없는 모든 끝(예외, 정의 밖의 반환값)에서 맡은 쓰기를 이미 끝냈거나 거둔 상태여야 한다.** 그래야 `delivery: "unknown"`의 `at`이 실은 시각의 상한이 되어 간격이 지켜진다. 그렇게 끝난 뒤에도 쓰기가 이어지는 포트를 붙이면 같은 요청이 간격보다 짧게 두 번 실릴 수 있다(위 "두드리지 않기").
- **`not_rebuildable`은 같은 실행 ID를 조회한다.** 새 요청 ID로 다시 만들지 않는다.
- **조립이 넘기는 장부 포트는 박자가 읽는 그 장부 객체다.** 표식은 장부 열기마다 따로 센다. 다른 열기의 객체에 표식을 적으면 이 열기에서 실은 시작을 장부가 가리지 못한다(`send-gate.md` "뒤 조각이 지킬 것").
- **`start_unmarked`는 다음 박자가 다시 시도한다.** 장부가 못 씀이면 다시 열 때까지 표식이 거절되므로 그동안 시작은 다시 나가지 않는다(닫는 쪽).
- **`stop_generation_mismatch`는 세대 맞춤 뒤 다른 조각이 낸다.** 종료는 새 세대의 비상 종료, 확정은 새 세대·새 요청 ID의 확정(그때는 이번 발행 시각을 판단과 같은 시계로 적는다).
- **`start_expired`는 D-90의 재료로만 쓴다.** 자리를 풀려면 접수 영수증이 한 번도 없음(장부의 읽기만이 아니라 실행기의 과거 점유 응답도 본다)과 그 뒤 전체 점유에 없음이 함께 성립해야 한다(`ledger.md` "D-90"). 접수 보류(`intake_closed`) 중에 한도가 지난 시작도 D-90이 접수 보류·봉투 시한·전체 점유를 한데 확인해 닫는다.
- **확정에 답이 없는 실행의 조회를 맡는다.** 확정을 다시 낸 뒤 지금의 수명 판단은 그 실행을 조회하지 않는다(위 "두드리지 않기").
- **`halted`를 본다.** `threw`이면 이미 돌려받은 항목을 반영하고, 결과 목록에 없는 지시를 다음 박자가 다시 본다(장부는 그대로다). 조립은 포트 묶음의 속성 접근이 던지지 않게 만든다(평범한 객체).
- **간격을 정한다.** 시작을 한 번이라도 다시 내려면 `resendEveryMs <= 19000`이어야 한다. 운영 값은 정해지지 않았다.

## 남는 한계

- **포트 안의 지연.** 내보내기 포트를 부른 뒤 실제로 싣기까지의 시간은 이 박자가 재지 못한다. 시작은 마지막으로 시계를 읽은 시각이 발행 + 19000ms 이하였다는 것까지만 이 박자가 지키고, 작업 기한의 여유와 싣는 순간의 한도는 내보내기 포트가, 실행기 쪽의 받는 시각은 봉투 모듈의 여유(11000ms)가 지킨다.
- **박자 사이의 시계 후퇴.** 시계의 하한은 한 박자 안에서만 유효하다. 앞 박자에서 `start_expired`였던 시작도 다음 박자의 시계가 뒤로 가면(발행 + 19001 → + 18000) 다시 나간다.
- **접수 보류 중 시한이 지난 시작.** 다시 나가지 않지만(`intake_closed` 뒤 `start_expired`) 그 실행은 D-90이 닫기 전까지 작업 슬롯을 쥔다.
- **다시 읽기가 막는 범위.** 앞 항목을 기다리는 동안 끼어든 쓰기(영수증, 정지, 새 종료)는 막는다. 다시 읽기와 내보내기 사이의 동기 포트(시계·접수·연결·서명) 안에서 일어난 쓰기는 보지 못한다.
- **받은 적 없는 실행의 종료.** 실행기가 시작을 받지 못한 채 종료만 적힌 실행은, 실행기가 모르는 실행의 종료에 답하지 않으므로 그 종료가 간격마다 다시 나간다. D-90이 그 실행을 닫기 전까지다.
- **`delivery: "unknown"`.** 실렸을 수 있다. 같은 요청 ID로만 다시 내므로 실행기에서 겹치지 않는다. 간격이 지켜지는 것은 내보내기 포트가 전달을 확정할 수 없는 모든 끝(예외, 정의 밖의 반환값)에서 맡은 쓰기를 이미 끝냈거나 거둔 경우다.
