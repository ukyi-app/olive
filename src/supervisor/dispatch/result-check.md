# 결과 검사의 한 박자 (`result-check.ts`)

`checking`에 머문 작업자 실행을 `ready_result`나 `failed_stopped`로 옮기는 감독 쪽 자리다. 실행마다 반영 전 결과 보고(`pendingReports`)를 모으고, 판정 자리(`resultVerdict`)가 통과로 낸 결과만 장부의 `markResult`로 판정한다. 반영 전 결과 보고 없이 기한이 지난 실행은 `markResult(null)`로 결과 없음을 판정한다(D-113). 기한은 종료 영수증 시각·복원 5단계를 받아들인 시각·그 실행기의 지금 연결이 인정된 시각 가운데 **가장 늦은 때부터** 세고, 그 실행기가 연결돼 있고 인정 뒤 재전송 한 주기(계약의 `RENEW_INTERVAL_MS`, 10초)가 지났을 때만 판정한다(D-123). 장부 시각만이 아니라 **이 프로세스의 단조 경과로도** 같은 기한과 주기가 지나야 한다. 더해 **그 연결에서 실행기가 그 실행을 물은 상태 조회에 실제로 답했고, 그 조회를 기한 시작 + 재전송 한 주기 이후에 실었고, 그 답이 그 실행을 `ready_result`라고 말하지 않았고, 감독이 받고 보관하지 못한 그 실행의 결과 보고가 없을 때만** 판정한다(장부 시각과 단조 경과 모두. 아래 "이미 받은 결과를 결과 없음으로 판정하지 않는다"). 인정된 연결 번호만으로는 실행기와 주고받을 수 있는지 모른다(아래 "인정된 연결 번호만으로 판정하지 않는다"). **판정은 확정이 아니고 게시 허가도 아니다.** 확정(`result_finalize`)은 수명 박자가 `settledResult`(판정 + 저장 자리와 함께 반영된 보고)를 보고 낸다(`life-loop.md` "확정"). 자리는 실행기의 정리 영수증으로만 풀린다.

순서기(`runtime/cycle.ts`)가 끊김 뒤, 수명 앞에서 부른다(`cycle.md` "한 박자의 차례" 3a). 그래서 같은 박자의 수명 박자가 이 판정을 보고 확정을 낸다. 소켓·타이머·시계·난수를 직접 쓰지 않는다. `now`는 순서기가 부르기 직전에 다시 읽은 장부 시계이고, 장부의 판정 시각(`updated_at`, 보고의 `applied_at`)과 기한 비교에만 쓴다. 기한은 정책 인자(`ResultCheckPolicy`)이고 운영 값은 감독 설정 한 자리(`src/main/supervisor.ts`의 `RESULT_CHECK`, T1 실측 전의 시험 숫자 90000ms, 아래 "감독이 모르는 끊김")다.

## 공개 면

```ts
resultCheckTick(ports: ResultCheckPorts, now: number, policy?: ResultCheckPolicy): ResultCheckTickResult   // 동기

ResultCheckPolicy = { reportWaitMs: number }   // 양의 안전 정수. 빠지면 결과 없음 판정 없음(조립은 반드시 넘긴다)

ResultCheckPorts = {
  ledger: Pick<Ledger, "listRuns" | "pendingReports" | "markResult">   // 읽기 둘, 쓰기 하나
  intake: Pick<Restorer, "intakeOpen">   // 조립의 접수 문(박자 유효 문 + 복원기의 접수)
  beatValid?: () => boolean              // 장부 호출 바로 앞. 빠지면 늘 유효(조립은 반드시 넘긴다)
  reach?: ResultReach                    // 결과 없음 판정의 기한 시작과 연결 조건(D-123). 빠지면 결과 없음 판정 없음(조립은 반드시 넘긴다)
}

ResultReach = {                          // ...At은 장부 시계, since...Ms는 단조 경과(0 이상 유한수). 모르면 null, 던지면 null과 같다
  restoredAt(): number | null            // 이 프로세스가 복원 5단계의 허가를 받아들인 시각
  greetedAt(executorId): number | null   // 그 실행기의 지금 인정된 연결이 인정된(greeted로 옮긴) 시각. 연결이 없으면 null
  sinceRestoredMs(): number | null       // 5단계를 받아들인 뒤의 단조 경과
  sinceGreetedMs(executorId): number | null  // 그 연결이 인정된 뒤의 단조 경과
  sinceSeenMs(runId): number | null      // 이 프로세스가 그 실행을 결과 없음 판정을 기다리며 처음 물은 뒤의 단조 경과(처음 0)
  answeredAt(executorId, runId): number | null  // greetedAt과 같은 연결에서 그 실행기가 답한(대조된) 상태 조회 가운데 그 실행을 물은 것 중 가장 늦게 실은 것의 실은 시각
  answeredState(executorId, runId): string | null  // 같은 답에서 실행기가 그 실행에 대해 말한 상태(계약 v1의 RUN_STATES)
  sinceAnsweredMs(executorId, runId): number | null  // 그 조회를 실은 뒤의 단조 경과
  unstoredResult(runId): boolean | null  // 감독이 받고 보관소나 장부에 닿았는지 모르는 그 실행의 결과 보고가 남았으면 true
}

resultVerdict(reports: PendingResult[]): { kind: "pass", resultDigest, reportId } | { kind: "wait" } | { kind: "conflict", digests }

ResultCheckTickResult =
  | { kind: "not_run", reason: "now_malformed" | "policy_malformed" | "tick_in_progress" | "intake_closed" }
  | { kind: "not_run", reason: "read_unknown", read: "runs" | "reports" }
  | { kind: "ran", runs: ResultCheckOutcome[], halted: null | "threw" | "intake_closed" | "beat_closed", haltedAt: string | null }
```

| 실행마다 (`ResultCheckOutcome`) | 뜻 |
|---|---|
| `judged` + `reportId`, `resultDigest`, `state` | 장부가 판정을 적었다고 답했다. `state`는 답의 실행 줄 상태(`ready_result`, 장부가 이미 판정을 마친 실행이면 그 뒤 상태) |
| `waiting` | 반영 전 결과 보고가 없고 기한 전이다(정책 인자가 없거나, 실행 줄의 `updatedAt`·지정 실행기나 `reach`의 사실을 모르거나, 그 실행기의 인정된 연결이 없거나, 인정 뒤 재전송 한 주기 전이거나, 그 연결에서 실행기가 그 실행을 물은 조회에 답하지 않았거나 그 조회를 기한 시작 + 한 주기 전에 실었거나, 그 답이 `ready_result`이거나, 감독이 보관하지 못한 그 실행의 결과 보고가 남았을 때도). 장부를 부르지 않았다 |
| `no_result` + `checkingSince`, `state` | 반영 전 결과 보고 없이 기한이 지나 장부가 결과 없음 판정을 적었다고 답했다(`state`는 `failed_stopped`). `checkingSince`는 판정에 쓴 실행 줄의 `updatedAt`이다. 조립이 감독 기록에 `result_check_alert`(`reason: "no_result"`) 한 줄을 남긴다 |
| `digest_conflict` + `digests`, `reports` | 서로 다른 digest의 반영 전 결과 보고가 있다. 장부를 부르지 않았다. 조립이 감독 기록에 `result_check_alert` 한 줄을 남긴다(실행마다 프로세스에서 한 번) |
| `refused` + `reportId`, `reason` | 장부가 거절했다(`transition_denied`, `reference_mismatch` 등). 결과 없음 판정이면 `reportId`는 `null`이다. 박자는 다음 실행으로 간다 |
| `ledger_failed` + `reportId`, `reason` | 장부가 적었는지 모른다(`threw`: 장부 호출이 던짐, `malformed_answer`: 답이 정의 밖). 그 자리에서 `halted: "threw"` |

결과에는 `checking`인 작업자 실행만 실행 목록의 차례대로 있다. 세션 실행과 다른 상태의 실행은 보지 않는다. 결과 보고의 저장 자리와 장부의 문구는 싣지 않는다.

## 판단의 차례

1. **박자 전체의 전제.** 진행 중인 박자가 없음(있으면 `tick_in_progress`), `now`가 양의 안전 정수, 정책 인자가 있으면 기한이 양의 안전 정수(`policy_malformed`), 접수 문이 열림(`intake_closed`), 실행 목록(`listRuns`)과 반영 전 보고(`pendingReports`)를 앎. 하나라도 아니면 `not_run`이고 장부를 부르지 않는다.
2. **모름은 판정하지 않는다.** 두 목록 모두 `known: true`이고 배열이어야 하고, 줄마다 칸을 한 번씩 읽는다. 실행 줄은 실행 ID(UUID)·종류(`worker`·`session`)·상태(장부의 상태 이름), 보고 줄은 보고 ID(UUID)·동작(보고 셋 중 하나), 결과 보고면 실행 ID·저장 자리(빈 문자열 아님)·digest(소문자 16진수 64자리)다. **한 줄이라도 읽지 못하거나 꼴이 틀리거나 같은 ID의 줄이 둘이면 그 목록 전체가 모름이다**(`read_unknown`). 보고 한 줄을 건너뛰고 판정하면 그 실행의 다른 digest를 보지 못한 채 판정하고, 장부는 그 보고를 충돌 기록으로 닫는다(`ledger.ts`의 `markResult`).
3. **실행마다 판정 자리.** `checking`인 작업자 실행마다 그 실행의 반영 전 결과 보고(장부의 차례: 받은 시각, ID)를 `resultVerdict`에 넘긴다. 보고가 없으면 `wait`, digest가 둘 이상이면 `conflict`, 정확히 하나면 `pass`(그 digest의 첫 보고 ID). `wait`이면 기한 시작(`waitFrom`)을 정한다: 실행 줄의 `updatedAt`(`checking`이 된 시각)·`reach.restoredAt()`·`reach.greetedAt(그 실행의 지정 실행기)` 가운데 가장 늦은 때다. 셋 중 하나라도 모르거나(포트 없음, null, 던짐, 양의 안전 정수가 아님, 실행 줄의 `executorId`가 빈 문자열이 아닌 문자열이 아님), `now − greetedAt < RENEW_INTERVAL_MS`이면 기다린다. 단조 경과 셋(`sinceSeenMs`를 맨 먼저 물어 처음 본 때를 남긴다)도 하나라도 모르거나(null, 던짐, 음수, 유한수가 아님), `sinceGreetedMs < RENEW_INTERVAL_MS`이거나, 셋 중 가장 짧은 것이 기한보다 짧으면 기다린다. 이어 답한 조회를 본다: `reach.answeredAt(지정 실행기, 그 실행)`이 양의 안전 정수가 아니거나, `now`보다 뒤이거나, 기한 시작 + `RENEW_INTERVAL_MS`보다 이르면 기다린다. `answeredState`가 계약 v1의 실행 상태가 아니거나 `ready_result`이면 기다린다. `sinceAnsweredMs`(다른 단조 경과보다 뒤에 묻는다)를 모르거나, 단조 경과 셋 중 가장 짧은 것 − `sinceAnsweredMs` < `RENEW_INTERVAL_MS`(그 조회를 단조 기준들 + 한 주기 전에 실었다)이면 기다린다. 마지막으로 `unstoredResult(그 실행)`이 `false`가 아니면(`true`, `null`, 던짐, 그 밖의 값) 기다린다. 기한 시작부터 `now`까지가 기한 이상일 때만(정각 포함) 결과 없음 판정으로 간다. 시계가 기한 시작이나 인정 시각보다 뒤면 경과가 음수라 기다린다. 통과 판정은 이 사실을 읽지 않는다.
4. **판정 하나.** 인자 `{ runId, resultDigest, reportId, now }`(결과 없음이면 `{ runId, resultDigest: null, now }`)를 만든 뒤 → `callAfterGate`(장부 포트 객체·`markResult`·인자 원소 얻기 → 문 → 호출 하나, `send-gate.ts`). 문은 접수 문 → 박자 유효 문 차례다(`gateOpen`). 접수 문을 얻기 뒤에 두어 얻기의 접근자 안에서 정지가 적용돼도 적지 않고(장부는 판정을 정지 중에도 받는다), 박자 유효 문을 맨 끝에 두어 접수 문 안의 읽기에 쓴 시간까지 박자 기한에 든다. 문 뒤에는 외부 코드가 없고 읽기부터 호출까지 `await`가 없다. 접수 문이 닫혔으면 `halted: "intake_closed"`, 유효 문이 닫혔으면 `halted: "beat_closed"`이고 그 실행의 장부 호출은 0회다.
5. **답.** 칸마다 한 번만 읽는다. `ok: false`와 장부의 거절 이름이면 `refused`. `ok: true`면 답의 실행 줄이 같은 실행 ID·같은 digest·판정 뒤 상태(`ready_result`·`cleanup_pending`·`finalized`)일 때만 `judged`, 결과 없음 판정이면 같은 실행 ID·digest `null`·`failed_stopped`일 때만 `no_result`(보고 ID 없이 부르면 장부는 `checking`에서 옮길 때만 `ok`다). 그 밖은 `ledger_failed`이고 박자를 멈춘다.

## 정한 것

- **`reportId`를 늘 넘긴다.** 장부가 그 보고가 이 실행의 반영 전 보고이고 digest가 같은지 대조하므로(아니면 `reference_mismatch`) 판정이 이 박자가 본 보고를 정확히 가리킨다. 확정을 여는 데에는 필요 없다: 빠져도 장부는 판정하면서 그 실행의 반영 전 결과 보고를 모두 반영해 `settledResult`가 값을 낸다(`life-loop.md` "뒤 조각이 지킬 것"). 같은 digest의 보고가 여럿이면 첫 보고의 ID를 넘기고 나머지는 장부가 같은 판정에서 함께 반영한다.
- **digest가 둘 이상이면 판정하지 않는다.** 어느 결과를 택할지 감독이 정할 근거가 없다(결과 보관은 둘 다 됐다). 장부의 `markResult`에 맡기면 판정한 digest 밖의 보고를 충돌 기록으로 닫아 되돌릴 수 없다. 그래서 반영 전 그대로 두고 경보만 남긴다. 그 실행은 관리자가 볼 때까지 `checking`으로 자리를 쥔다.
- **접수 문을 본다.** 복원 5단계 전, 정지 중, 허가 폐기 때는 판정하지 않는다. 장부는 판정을 정지 중에도 받지만(쓰기 모드 `continue`), 수명 박자가 확정을 접수가 열렸을 때만 적으므로 판정만 앞당겨도 자리는 풀리지 않는다. 정지가 풀린 뒤 복원 판정과 같은 문을 지나서 판정한다. 박자 처음과, 장부 호출마다 그 바로 앞의 문 안에서 본다(앞 실행의 장부 호출이나 장부 포트를 얻는 접근자 안에서 닫힐 수 있다).
- **박자 안에서 같은 실행은 한 번만 판정한다.** 실행 목록에 같은 실행 ID가 둘이면 목록 전체가 모름이다. 판정이 끝난 실행은 다음 박자의 목록에서 `checking`이 아니라 다시 판정하지 않는다.
- **결과 없음 판정은 반영 전 결과 보고가 하나도 없을 때만이다(D-113).** 기한 직전에 보고가 오면 그 박자는 그 보고로 통과 판정을 한다. 영수증 쪽 기준은 실행 줄의 `updatedAt`이다: `checking`으로 오는 길은 `completed` 종료 영수증 하나라 그 시각이 영수증을 받은 시각이고, 영수증의 전이와 같은 트랜잭션에서 적힌다.
- **실행기가 장부에 닿을 수 없던 시간은 기한에 넣지 않는다(D-123).** 기한은 종료 영수증·복원 5단계를 받아들인 때·그 실행기의 지금 연결이 인정된 때 가운데 가장 늦은 때부터 센다. 실행기는 연결이 맞춰져 있을 때만 결과 보고를 보내고 받음 확인이 없는 보고를 마지막 송신에서 `RENEW_INTERVAL_MS`가 지나면 다시 보낸다(`src/executor/worker.ts`의 `transmit`·`tick`). 그래서 감독이 멈춰 있던 동안, 복원이 끝나기 전, 연결이 끊긴 동안을 기한에 넣으면 실행기가 다시 보낸 보고가 닿기 전에 결과 없음으로 판정하고, 실행기는 그 확정으로 작업 폴더를 지워 결과가 사라진다. 판정 전에는 그 실행기의 인정된 연결이 있고 인정 뒤 `RENEW_INTERVAL_MS`가 지났는지(정각부터 지난 것으로 본다)를 본다. 사실은 조립이 넘긴다(`boot.ts`의 `reach`): 5단계 시각은 조립이 5단계를 받아들인 순간 공유 시계를 하한을 올리지 않고 읽은 값(`peek`)이고, 인정 시각은 서버가 그 연결을 배정 후보(`candidate`)로 조립의 `deliver`에 넘긴 순간(판단이 연결을 `greeted`로 옮긴 같은 동기 구간) 조립이 읽은 `peek` 값이다. 연결 표의 `greeting.at`(인사 바이트를 받은 시각)은 서명 검증을 기다린 시간(맞춤부터 인사 판단까지 기본 상한 25초)만큼 이르므로 쓰지 않는다. 서버의 `recognized(실행기)`가 낸 연결 번호로 그 기록을 찾고, 철회(`withdrawn`)되면 지운다. 다시 붙으면 새 연결의 인정 시각이 된다. 결과 없음 판정에는 `reportId`를 넘기지 않는다(반영할 보고가 없고, 장부는 판정하면서 그 실행의 반영 전 결과 보고를 모두 닫는다).
- **벽시계만 앞으로 뛰어도 판정하지 않는다(D-123).** 장부 시계(공유 시계)는 벽시계가 앞으로 뛰면 그만큼 앞선다. 그래서 같은 두 조건을 조립의 단조 시계(`deps.monoNow`, 운영은 `performance.now`)로도 본다: 5단계를 받아들인 순간과 인정 순간에 단조 시각을 함께 적고, 종료 영수증은 장부 시각뿐이라 결과 검사가 그 실행을 처음 물은 단조 시각을 그 기준으로 쓴다(처음 물은 때는 영수증을 받은 때보다 이르지 않다). 처음 본 기록은 박자가 끝까지 돈 뒤 기다림으로 끝나지 않은 실행의 것을 지운다. 그래서 정상 흐름에서도 결과 없음 판정은 영수증 뒤 첫 결과 검사 박자부터 센 단조 기한까지 늦어질 수 있다(이른 판정 쪽으로는 틀리지 않는다).
- **인정된 연결 번호만으로 판정하지 않는다.** 상대가 사라졌는데 FIN이 오지 않은 연결을 서버는 인정된 연결로 둔다. 직접 연결이면 TCP keepalive(olive #77: 첫 탐침 30초 + 간격 10초 × 4, `TCP_USER_TIMEOUT` 70초)가 닫지만, 감독 소켓의 TCP 상대가 중계이면 중계의 커널이 탐침에 답해 연결이 남는다. 그래서 결과 없음 판정 전에 그 연결에서 실행기가 실제로 답한 상태 조회를 본다. 조회는 수명 박자가 기다리는 `checking` 실행에 같은 실행 ID로 낸다(`life-loop.md` "조회", `cause: "result_wait"`, 간격 `answerTimeoutMs`). 조립은 내보내기 포트가 조회를 등록부에 넣는 순간(연결에 싣기 직전)의 연결 번호·`peek`·단조 시각을 요청 ID에 적고, 답 줄이 그 조회의 답을 대조하면(`status_matched`) 그 연결의 답한 조회로 적는다(같은 연결에서 가장 늦게 실은 것, 철회면 지운다). 실은 시각을 쓰는 까닭: 실행기는 조회를 받은 뒤에 답을 만들므로 실은 시각이 답을 만든 때의 하한이다. 실행기는 같은 연결에 먼저 실은 보고 뒤에 답을 싣고(TLS 한 흐름), ack가 없는 보고를 마지막 송신에서 `RENEW_INTERVAL_MS`가 지나면 다시 보낸다. 그래서 기한 시작 + 한 주기 이후에 실은 조회에 답했으면 그 전에 다시 보낼 기회가 있던 결과 보고는 답보다 먼저 닿았다. 운영 기한 90초와 keepalive 한계(`src/main/supervisor.ts`의 `KEEPALIVE_DETECT_MS`)의 관계는 `boot-result-check.test.ts`가 그대로 묶는다(직접 연결에서 끊김을 알기 전에 기한이 차지 않게 하는 여유다). 중계 뒤의 끊김은 `boot-relay.test.ts`가 keepalive를 켠 소켓과 끈 소켓에서 본다.
- **이미 받은 결과를 결과 없음으로 판정하지 않는다.** 답한 조회 하나만으로는 그 실행의 결과가 장부에 닿을 수 없음을 모른다. 실행기는 결과 보고를 만든 실행을 `ready_result`로 답하고(`src/executor/worker.ts`의 `statusOf`), 감독이 그 보고를 받고도 보관소가 `unknown`을 내면(`receipts.ts`의 `result_unknown`) 반영 전 보고 목록은 빈다. 그때 결과 없음으로 판정하면 보관소가 돌아온 뒤 같은 보고를 장부가 `transition_denied`로 영영 거절하고, 실패 확정을 받은 실행기는 그 실행을 정리한다. 그래서 (1) 근거는 그 실행 ID를 물은 조회의 답만 쓴다: 같은 실행기의 다른 실행만 물은 답은 그 실행의 보고가 앞서 닿았다는 근거가 아니다. (2) 그 답이 그 실행을 `ready_result`라고 말했으면 기다린다. (3) 감독이 받고 보관소나 장부에 닿았는지 모르는 그 실행의 결과 보고가 남았으면 기다린다. 조립은 답 줄의 영수증 처리 결과로 이 기억을 메모리에 쥔다: `result_unknown`(보관 모름·장부 읽기 모름), 결과 보고의 `ledger_failed`·`ledger_refused`(보관 뒤 장부가 던지거나 거절. `ledger_unwritable`처럼 장부에 닿지 않은 거절이 있다)는 적고, 같은 보고 ID를 장부가 받으면(`ack`·`applied_without_ack`) 또는 보관 전에 확정 거절하면(`result_refused`) 지운다. 실행 ID 없이 장부 실패가 오거나 적다 던지면 그 뒤로는 모름이라 이 프로세스는 결과 없음 판정을 하지 않는다. 기억은 감독이 다시 뜨면 빈다(실행기는 ack를 받을 때까지 같은 보고를 다시 보낸다). 통과 판정은 이 사실을 읽지 않는다: 반영 전 보고가 있으면 그 digest로 판정해 결과를 보존한다.
- **같은 실행·연결의 미결 조회는 하나다.** 수명 박자는 답 없는 실행을 `answerTimeoutMs`마다 새 요청 ID로 다시 묻는다. 조립은 등록부에 조회를 더할 때마다 같은 받는 이·연결·실행 ID 집합의 앞 요청 ID 항목을 끝낸다(`query-book.ts`의 `supersededBy`). 대체된 조회의 늦은 답은 대조할 항목이 없어(`unknown_query`) 장부에도 이 근거에도 닿지 않는다. 내보내기 포트는 쓰기 전에 더하므로 끝내 싣지 못한 새 조회도 앞 조회를 끝낸 뒤다(그 연결에서 `answerTimeoutMs` 넘게 답이 없던 조회의 답을 버리는 쪽이다).
- **늦게 온 결과 보고는 장부가 거절한다.** `failed_stopped`가 된 실행의 결과 보고는 장부가 `transition_denied`로 거절한다(`ledger.ts`의 `#resultDisposition`). ack가 없어 실행기가 계속 다시 보낸다. 판정은 되돌리지 않는다.
- **확정은 수명 박자가 낸다.** 결과 없음으로 판정한 실행의 확정 본문은 `outcome` `failed`(사유 `requested`의 취소 지시가 적혔으면 `cancelled`), `stored_at`은 이 판정의 `now`다. 사유 없는 취소 지시(사유 칸이 생기기 전의 옛 줄)가 있으면 `outcome`을 정하지 못해 확정하지 않는다(`outcome_unknown`, `life-loop.md` "실패 확정").
- **재시작 뒤에도 같은 길이다.** 복원 3단계는 `checking` 실행(`resumeChecks`)과 반영 전 보고를 다시 꺼내지만 판정하지 않는다. 이 박자가 매 박자 장부에서 같은 두 목록을 읽으므로 따로 이어 받을 것이 없다.

## 관리자 결정 대기

보고가 있는 실행의 판정 갈림은 모두 `resultVerdict` 한 함수에 있다. 답에 따라 이 함수를 바꾼다.

- **Q-H1(감독이 직접 검사할 범위):** 지금은 "반영 전 결과 보고가 정확히 한 digest인가"만 본다. 역할 일치·출처 참조·비밀 패턴은 보지 않는다.
- **Q-H5(결과 `outcome`이 `failed`·`needs_input`인 결과):** 장부의 보고 줄에는 결과의 `outcome`이 없고 이 박자는 보관소의 본문을 읽지 않으므로 digest가 있는 결과는 모두 통과다. `outcome`으로 가르기로 하면 이 함수와 함께 보관소 읽기 포트가 필요하다.
- **기한의 숫자:** `RESULT_CHECK.reportWaitMs`는 T1 실측 전의 시험 숫자다. 실측 뒤 조정한다.

## 남는 한계

- **충돌한 실행은 자리를 쥔다.** 경보 뒤에 그 실행을 닫는 길은 아직 없다(관리자 닫기는 종료 확인이 있는 실행을 받지 않는다, `ledger.md`).
- **연결이 돌아오지 않는 실행기의 `checking` 실행은 판정하지 않고 자리를 쥔다.** 인정된 연결이 없거나, 연결은 인정돼 있는데 실행기가 조회에 답하지 않으면 기한이 얼마나 지나도 결과 없음으로 옮기지 않는다(D-123). 그 실행기를 등록표에서 뺀 경우도 같다. 그동안 수명 박자는 `answerTimeoutMs`마다 그 실행을 묻는다.
- **보관하지 못한 결과 보고가 끝내 장부에 닿지 않으면 그 실행은 자리를 쥔다.** 같은 보고 ID가 ack되거나 보관 전에 확정 거절될 때까지 결과 없음 판정을 하지 않는다(보관 뒤 장부의 확정 거절도 지우지 않는다). 기억은 메모리뿐이라 감독이 다시 뜨면 빈다.
- **답 줄의 처리기가 결과 보고에서 던지면 그 보고는 기억에 남지 않는다.** 답 줄은 처리기가 던지면 기록하지 않는다(`answers.ts`의 `passReceipt`). 처리기의 결과 보고 길은 장부 읽기·보관·장부 쓰기를 예외 처리 안에서 부르므로 실제로는 포트 접근자가 던질 때뿐이다. 실행기는 ack가 없는 보고를 다시 보낸다.
- **첫 관측 기록의 정리 대상을 읽지 못한 박자는 결과 없음 판정을 하지 않는다.** 조립은 박자 전에 그 목록을 읽고, 읽지 못하면 `reach`를 넘기지 않는다. 통과 판정은 그대로다.
- **5단계 시각을 읽지 못하면 그 프로세스는 결과 없음 판정을 하지 않는다.** 조립이 5단계를 받아들인 순간 공유 시계의 `peek`이 `ok`가 아니면 `restoredAt`이 null로 남는다. 다시 뜰 때까지 보고 없는 `checking`은 자리를 쥔다.
- **기한이 재전송 한 주기 이상이면 "인정 뒤 한 주기" 조건은 기한 시작에 이미 든다.** 운영 값(90000ms)에서는 기한 시작 조건만으로 갈린다. 기한을 10000ms보다 짧게 두면 인정 뒤 10000ms가 아래 한계다.
- **기한의 기준이 `updatedAt`이다.** 장부의 `recordBudget`은 상태와 무관하게 `updatedAt`을 바꾼다. 지금 부르는 코드는 없지만, `checking` 줄에 부르면 기한이 그만큼 늦어진다(이른 판정 쪽으로는 틀리지 않는다).
- **결과 없음으로 판정한 실행의 자리는 확정·정리로만 풀린다.** 수명 박자가 `outcome`을 정하지 못하는 `failed_stopped`(`life-loop.md` "실패 확정")는 자리를 쥔다.
- **판정과 장부 호출 사이에 새 보고가 끼는 것은 막지 못한다.** 박자는 동기이고 보고는 소켓 사건으로만 오므로 실제로는 끼지 않는다. 장부 포트 안에서 다시 보고를 적는 경우는 장부가 다른 digest의 보고를 충돌로 닫는다.
- **경보 기억은 메모리뿐이다.** 감독이 다시 뜨면 같은 충돌에 경보를 한 줄 더 남긴다.
