# 결과 보관소의 파일 백엔드 (`result-store-file.ts`)

결과 보관소 판단(`result-store.ts`, D-78)의 백엔드 포트 `ResultBackend`를 로컬 폴더 하나 위에 구현한다. **키 하나는 파일 하나이고, 새 파일은 임시 이름에 끝까지 쓰고 fsync한 뒤 `link`로만 키의 이름을 얻는다.** 무엇을 받아들이고 누구에게 내주는지(소유자, digest, 판정 포트, 고아 정리)는 판단이 정한다. 이 모듈은 바이트를 두고 읽는 것만 한다. 폴더의 경로와 기록의 상한은 인자로 받고, 환경 변수·시계·난수를 읽지 않는다.

## 공개 면

```ts
createFileResultBackend({ dir, maxRecordBytes, files? }): FileBackendAnswer
  // { status: "ok", backend: FileResultBackend } | { status: "invalid", reason: "dir" | "max_record_bytes" }
  // 파일 시스템을 부르지 않는다. 폴더를 만들거나 권한을 바꾸지 않는다.

FileResultBackend extends ResultBackend   // 판단에 그대로 넣는다
  // 답의 갈래는 포트와 같고, unknown에만 reason이 붙는다:
  // invalid_key | invalid_input | too_large | not_file | no_dir | changed | io

FilePort, nodeFilePort   // 파일 호출의 꼴과 node:fs 구현. 시험이 중간 실패를 넣는 자리
```

- `dir`: 정규화된 절대 경로(`/a/../b`, `/a/`, 상대 경로, NUL은 `invalid`). 폴더가 이미 있어야 한다. 없으면 연산마다 `unknown(no_dir)`이다.
- `maxRecordBytes`: 판단이 넘기는 기록(머리 길이 4바이트 + 머리 + 본문) 하나의 상한. **운영 값은 정하지 않았다.** 본문의 상한은 계약 v1의 `RESULT_MAX_BYTES`(16KiB)이고 머리는 수백 바이트라, 조립하는 쪽이 그보다 넉넉한 값을 고른다. 넣기는 이보다 크면 파일 시스템을 부르기 전에 거절하고, 읽기는 이보다 큰 파일을 읽지 않는다(`too_large`).

## 키와 파일

키는 판단이 만드는 `result/<UUID>`(소문자 16진, 8-4-4-4-12) 꼴만 받는다. 파일 이름은 `<dir>/<UUID>`이고 임시 이름은 `<dir>/.<UUID>.partial`이다.

- 꼴이 아닌 키(빈 이름, 경로 구분자, `..`, 대문자, 뒤에 붙은 글자, 너무 긴 이름, 문자열이 아닌 값)는 **파일 시스템을 부르기 전에** `unknown(invalid_key)`이다. 이 꼴은 경로 구분자와 `..`를 담을 수 없어 파일 이름이 늘 `<dir>` 바로 아래다.
- 포트의 답에는 "꼴이 틀린 키"의 갈래가 없다. 그래서 `unknown`에 사유를 붙였다. 판단은 `status`만 보므로 모름으로 읽고, 사유는 시험과 진단이 본다(아래 "포트의 꼴").
- `keys(prefix)`는 폴더 안에서 UUID 꼴인 이름만 `result/<UUID>`로 바꿔 접두로 거르고 정렬해 낸다. 임시 이름(점으로 시작)과 모르는 이름은 내지 않는다. **UUID 꼴인데 일반 파일이 아닌 항목(폴더, 링크)은 낸다.** 판단의 목록(`listStored`)이 그 항목을 `unknown`으로 드러내고 고아 정리가 지우지 않게 하려는 것이다.

## 보장 1: 새로 두기는 원자적이고 있는 것을 덮지 않는다

`putNew`의 순서:

1. 키의 이름을 `lstat`한다. 일반 파일이 있으면 `exists`(아무것도 바꾸지 않는다), 다른 종류가 있으면 `unknown(not_file)`.
2. 임시 이름을 `O_CREAT|O_EXCL|O_WRONLY|O_NOFOLLOW`, 0600으로 연다. 이미 있으면(끊긴 앞선 넣기의 찌꺼기) 지우고 한 번만 다시 연다. `O_EXCL`은 그 자리의 링크를 따라가지 않아 폴더 밖에 쓰지 않는다.
3. 끝까지 쓴다(짧은 쓰기는 이어 쓴다) → 파일 `fsync` → 닫기.
4. `link(임시, 키)`. 이미 있는 이름을 덮지 않는다: `EEXIST`면 임시를 지우고 `exists`.
5. 붙은 이름의 dev·inode가 3에서 쓴 파일과 같은지 본다. 다르면 `unknown(changed)`이고 그 파일을 지우지 않는다.
6. 임시 이름을 지우고 폴더를 `fsync`한다. 폴더 `fsync`까지 성공해야 `stored`다.

- 1~4의 어디서 실패해도 `unknown`이고 키의 이름은 생기지 않는다(임시 이름은 지운다).
- 6의 폴더 `fsync`가 실패하면 `unknown`이지만 **이름은 이미 보인다.** 지우지 않는다. 판단은 다음 넣기에서 `exists`를 받고 다시 읽어 대조한다(`storeResult`의 재보관 길).
- 프로세스가 중간에 죽으면 남는 것은 임시 이름뿐이다. 키로 보이지 않고(`keys`·`has`·`read`), 같은 키의 다음 넣기가 지운다. 다른 키의 찌꺼기는 이 모듈이 치우지 않는다(정리 정책은 정하지 않았다).
- 4와 6 사이에서 죽으면 키와 임시 이름이 둘 다 남는다. 키는 다 쓰고 fsync한 바이트이고, 판단의 재보관과 고아 정리가 다룬다.

## 보장 2: 읽기 실패는 "없음"이 아니다

`absent`는 **그 이름이 없고(`ENOENT`) 폴더가 있으며 폴더라고 확인했을 때만**이다. 그 밖은 모두 `unknown`이다.

| 상황 | 답 |
|---|---|
| 폴더가 없음, 폴더 자리에 파일 | `unknown(no_dir)` 또는 `unknown(io)` |
| 권한, I/O 오류, 그 밖의 오류 | `unknown(io)` |
| 키 자리에 폴더·심볼릭 링크·장치 | `unknown(not_file)`(따라가지 않고, 지우지 않는다) |
| 파일이 `maxRecordBytes`보다 큼 | `unknown(too_large)`(읽지 않는다. `has`는 `present`) |
| 읽는 사이 파일이 짧아짐 | `unknown(changed)`(짧은 바이트를 내지 않는다) |

- 읽기는 `O_RDONLY|O_NOFOLLOW|O_NONBLOCK`으로 연 뒤 `fstat`으로 일반 파일과 크기를 확인한다. `O_NONBLOCK`은 키 자리에 FIFO가 있을 때 여는 데서 멈추지 않게 한다.
- `readRange(key, offset, length)`: `offset`·`length`는 음이 아닌 안전 정수만 받는다(아니면 파일 시스템을 부르기 전에 `unknown(invalid_input)`). `[offset, offset+length)`를 파일 끝에서 자르고, `offset`이 끝 이상이면 빈 바이트의 `ok`다. 합이 안전 정수를 넘어도 끝에서 자른다.
- `remove`는 일반 파일만 지운다. 지운 뒤 폴더 `fsync`까지 성공해야 `removed`다.
- 메서드 안에서 예상 밖의 것이 던져도 `unknown(io)`로 옮긴다. 밖으로 던지지 않는다.

## 판단의 시험이 쓰는 가짜와의 대조

판단의 시험(`test/supervisor/scheduler/result-store.test.ts`)의 메모리 가짜는 그 파일 안의 클래스라 가져올 수 없다. 이 모듈의 시험은 그 가짜의 고장 없는 동작을 옮긴 `MemoryBackend`와 파일 구현에 **같은 시험**을 돌린다: 포트 연산 다섯 묶음과, 판단의 연산(보관·재보관·충돌·읽기·범위 읽기·남의 소유자·목록·지우기·고아 정리)을 차례로 부른 답 전체가 같은지.

다른 점은 포트의 문서가 정하지 않은 입력뿐이다. 가짜의 `readRange`는 음수 `offset`을 `Uint8Array.slice`처럼 끝에서부터 읽지만, 파일 구현은 `unknown(invalid_input)`이다. 판단은 음이 아닌 정수만 넘긴다(`listedEntry`의 `readRange(key, 0, 4)`와 `readRange(key, 4, 머리 길이)`).

## 두 프로세스

전제: **이 폴더를 쓰는 프로세스는 감독 하나다.** 포트가 동기라 한 프로세스 안에서는 호출이 겹치지 않는다. 이 모듈은 잠금을 두지 않으므로 두 프로세스가 같은 폴더를 쓰는 것을 막지 않는다. 그때:

- **있는 키를 덮지는 않는다.** `link`가 커널에서 `EEXIST`로 막는다.
- **같은 키를 동시에 넣으면 다 쓰이지 않은 바이트가 그 키로 보일 수 있다.** 임시 이름이 키마다 하나라, 한쪽이 다른 쪽의 임시 파일을 찌꺼기로 보고 지운 뒤 새로 만들 수 있다. 5의 inode 대조가 이 호출이 쓴 파일이 아님을 알아채면 `unknown(changed)`이지만, 다른 쪽이 아직 쓰는 파일이 그 키에 붙는 순간은 막지 못한다. 판단의 `storeResult`는 넣은 뒤 다시 읽어 머리와 digest를 대조하므로 그 기록을 `stored`로 치지 않는다. 읽는 쪽은 그 순간 잘린 기록을 볼 수 있고, 판단은 그것을 `corrupt`·`absent`·`unknown`으로 답한다.
- 같은 폴더를 두 프로세스가 쓰지 않게 하는 것은 배포의 일이다(감독 Deployment의 한 벌, 보관 폴더의 볼륨). 이 모듈은 그것을 확인하지 않는다.

## 정하지 않은 것

D-78이 정하지 않은 것을 이 모듈도 정하지 않는다: 보관소의 자리(어느 볼륨, 폴더의 소유자와 권한), 만료·잊기·사본·정리의 경계, D-22 원문 보관 시계와의 관계. 폴더는 부르는 쪽이 만들고 경로를 넘긴다. `maxRecordBytes`의 운영 값도 부르는 쪽이 정한다.

- 볼륨이 빠져 마운트 지점이 빈 폴더로 남으면 그 폴더는 "있는 폴더"라 없는 키는 `absent`로 읽힌다. 이 모듈은 마운트를 확인하지 않는다.
- `link`를 지원하지 않는 파일 시스템에서는 모든 넣기가 `unknown(io)`다.

## 포트의 꼴

포트(`ResultBackend`)는 고치지 않았다. 꼴이 틀린 키에 "모름"과 구별되는 갈래가 있으면 판단도 그것을 가를 수 있다. 필요하면 포트의 답에 `{ status: "invalid" }`를 더하는 것이 다음 꼴이다. 지금 판단은 꼴이 맞는 키만 만들므로 이 갈래가 실제로 나오지 않는다.
